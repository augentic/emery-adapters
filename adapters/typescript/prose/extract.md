# TypeScript / JavaScript source extract

This prompt runs once per seam of a bound `typescript` source. The caller has parsed the tree and decided its structure before this call: the message names the seam's surfaces — where control enters the source from outside the process: a route, a command, a job, a consumer, an exported API, the process bootstrap — each with the module a caller enters it at, the lines that register it, the stem and the id its claims lead with, and the modules it reaches; lays the modules those surfaces reach into the message in full, every line numbered, or lists the ones too large to lay; lists the boundaries those modules spell as values of their own; lists the packages they import; and lists the calls they make through those packages. Your job: read what is laid, follow each surface from its entry through what it reaches, and emit one Evidence document covering the behaviour a caller observes through the seam's surfaces, each behaviour under the surface whose caller observes it, once. A tree small enough for one message is one seam over every module and every surface it exposes; a larger tree is one seam per stem, over the modules its surfaces reach; a tree the caller finds no surface in is one seam over every module under the one stem the message names — or, past the budget of one message, one seam per top-level directory under that directory's name — read as a library is read, for what its exports do for a caller; an inline value is one seam mined whole, with no surface named, read for every surface it exposes. The caller joins the calls' answers into the source's one document, and the engine deterministically reconciles it with every other bound source's Evidence into the specification — see [From sources to a spec](reconciliation.md).

Everything this call needs is in this prompt, in `claims.md`, which the system prompt carries, and in the message. The worked examples under [`references/examples/`](references/examples/README.md) are the only documents to load, and only when a claim's shape is still unclear after the worked example below: the README's table names the one nearest the surface, and one is enough.

## Inputs

- **The surfaces** — one line each: `` Surface `<name>` — entry `<module>` — stem `<stem>`: <notes>; id `<id>`; reaches <modules> ``. The notes say where the surface is registered (the lines, the function or method, the package the receiver comes from), the lines of its handler when it is a function at the registration, the hooks folded into it (`worker.on("failed")`), or the methods an exported class carries. The `id` is what every `requirement` and `criterion` of the surface leads with — the stem alone when the surface is the stem's only one, the stem extended by what tells it apart when several share the stem (`orders.get-id`, `orders.place-order`); a class's line gives `ids`, one more per public method (`money.add`). `reaches` names the modules the surface's code reaches beyond its entry — the ones read for its rules — or says it reaches nothing beyond its entry. `start` is the process bootstrap — the entry module the manifest names or the tree's conventional entry — claimed for what those the program serves observe of it as a whole: a rule applied to every request, a health or status answer the source itself states, a setting it refuses to run without; how it readies itself, reaches other systems, and shuts down is the design's, in `excerpt` and `call` claims. When the caller found no surface, the message says so in place of the surface lines and names the one stem every `requirement` and `criterion` id leads with: read the modules as a library — each export for what it does for a caller — and name each behaviour for the export that exhibits it.
- **The modules** — the production modules the seam reaches, the entry first, laid out in full with every line numbered, or listed by path when they are too large to lay out. Every `path` you anchor names one of them; a claim anchored elsewhere is refused. When a module is laid out, cite `#L<n>` from the numbers shown and read nothing again; when it is listed, read it from `$SOURCE_DIR`. When the caller could not follow an import — a specifier naming no module of the tree, a module loaded by a computed name — the message says so and the rest of the importing module's directory, or of the directory the load spells, follows the closure, so what the import names is still within reach; read them for that alone.
- **Data files** — the `.json` files the modules import by relative path, each with the module importing it, laid after the modules (or listed when too large): the values the code reads from one — a tariff table, a mapping, a schedule — are the source's own, so a `criterion` may cite a value there at the line that holds it, while a `requirement` anchors in the module that reads it. Absent when the modules import none.
- **Boundaries** — every value the modules spell as a value of its own, at its exact anchor: a `process.env` read with the default beside it, a named constant, a pattern literal, a class field's initializer, an enumeration or a settings object written out — a status set, a placeholder list, a server's timeouts, a schema's defaults — collapsed to one line with its values in it. This is the list a `criterion` is drawn from.
- **Packages** — the bare specifiers the modules import, with the names bound to each and the modules binding them.
- **Calls** — every call the modules make through a package, grouped by callee with the lines of its sites (`` `pg:Pool.query` in `src/repositories/orders.ts` at L53-L56, L61 ``), less what is structure: constructions, registrations, mounts, lifecycle calls, and what a module-level declaration makes. This is the list a `call` is drawn from, and its `callee` is spelled as the list spells it.
- **Decision points** — every guard, switch, conditional, throw, catch, and timer the modules turn on, each at its lines with its text and the function it runs in (`` `src/orders/place.ts#L51-L53` — `if (items.length === 0)` in `placeOrder` ``). This is where a `requirement` anchors: at a decision point, at a `return` that yields a function's result, at the line that opens a function or method — its head, where a behaviour its whole body is — at a listed call or a package's construction, at a boundary or a line that applies a named constant (the cutoff computed from `OVERDUE_DAYS`), at a step the function takes into the tree — a call for its effect alone (a write, a delete, a publish, its value discarded), one it awaits (a lookup, a fetch), or one whose result it binds (`const users = listUsers(..)`) — at the code a stated behaviour names, or at a surface's registration or handler lines — the caller holds every `requirement` to those lines, and one anchored elsewhere comes back to re-anchor or drop. A step into the tree anchors what the caller does with it — the write, the publish, the value it awaits — and a behaviour the callee decides (a throw, a branch on its input) is the callee's requirement, anchored at its decision, however many callers step into it; a function-local constant a behaviour applies is cited as a criterion where it is spelled. A line that only wires or assigns — a field set, a value passed on, a value computed from the ones in hand (a subtotal reduced, a total rounded) — is no requirement's anchor: the computation is claimed at the function's head or its `return`; what `start` constructs with a boundary's value — a client, a connection, an agent — is an `excerpt` at that construction, the client's shape and the keys it reads, and never a requirement: what the program does through it is the requirement, claimed where the code decides that. Absent when the modules decide nothing.
- **Stated behaviours** — what the tree's own tests state about the seam's modules, each at its line: a test case's title under its suites' titles (`` `test/money.test.ts#L23` — Money › add › rejects a currency mismatch ``), a feature file's scenarios under its feature. The test files follow the laid modules, laid when they fit and listed otherwise, so their assertions can be read for the values they hold. A stated behaviour the laid code confirms is a `requirement` anchored at the code that exhibits it — never at the test — where that code is behaviour a caller of a surface observes, with an id named for that code and a statement the test's sentence leads, made present tense, in the domain's words the test already uses (`rejects a currency mismatch`, `No order is placed when the line items are empty`), the code's identifiers standing nowhere in it; a test over how the program readies itself, reaches another system, or shuts down — a secret or credential loaded, checked for emptiness, or watched for rotation, a reference table prefetched or refreshed, a client constructed, a retry policy, a startup or shutdown hook — backs the `excerpt` and the `call` at that code for the design and never makes it a `requirement`; a stated behaviour the code does not hold is not invented, and a test that states nothing the code does is left alone. Absent when the tree carries no test.
- **`$SOURCE_DIR`** — read-only view of the bound source root, needed only for a module the message lists rather than lays out. Absent when the source is an inline `value` (the seam is then in the message).
- **Source name** — the kebab-case name the engine passed on the WIT bindings, which the specification cites the source by.

Nothing outside the bound source is reachable; writes back into `$SOURCE_DIR` are denied.

## Reading the modules

Read once, then answer: each surface's registration and handler at the lines the surface line gives, then each module its line says it `reaches`, once each. A module a surface reaches is read for that surface's rules as the handler is: a mapping's arms, and what a fetch's failure leaves the caller with, are `requirement`s under the surface that reaches it; the fetch's retry, a secret parsed at startup, and the interval that re-runs the fetch are the `call`'s and the `excerpt`'s to carry, and a `call` the design needs is claimed whether or not a requirement stands beside it. What the tree does not hold — a package's internals, a declaration the tree does not carry — is not read and not invented.

**Where behaviour starts.** The surface line points at it: a route's handler or controller method; a command's action; a job's or consumer's callback; an exported API's function or class. From there follow imports outward through the laid modules: the services the handler calls, the repositories and clients they use. Under a dependency-injection container (Nest `@Injectable()`, `inversify`, `tsyringe`) a constructor parameter names a token; what runs is the provider the production module binds it to — follow the binding, not the parameter type.

**The entry layer.** What sits between the caller and the handler is this surface's behaviour where the surface itself mounts it: middleware the route or router mounts (a guard on one route, a rate limit on one router, a body parser or `zod` / `joi` / `class-validator` validation at the route), parameter sourcing (path, query, header, or body, and the coercion applied — `Number(req.query.limit)`), and what the handler itself returns on failure. Middleware mounted for every route — `app.use(auth)`, an error handler that maps every error class to a status, a request log — is `start`'s: claimed once, where it is mounted, for what it does to every request. A route seam names it by its key (`authenticate`, `errorHandler`) where a behaviour depends on it — the 401 a route's caller sees is the global guard's, not the route's — and never claims it again.

**The boundary between surfaces.** Decide it once, by this rule, and do not revisit it:

- The **`start` surface** owns what the program does as a whole, and is claimed for what those it serves observe of it: what every request gets from middleware mounted for every route (the global guard's 401, the body limit's 413, the error mapping's statuses, the request log's line), a health or status route a dependency serves for it where the source states its path or its answer, and a setting it refuses to run without. A route with a handler of the source's own, a health route among them, is a surface of its own, never `start`'s. How it readies itself, reaches other systems, and shuts down is the design's, never a `requirement`, as [claims.md](claims.md) has it: a credential or a token loaded, cached, or rotated; a reference table prefetched or refreshed on a timer; a client, a pool, or a connection constructed; a consumer subscribed; a heartbeat or status log; a signal or `uncaughtException` handler; a drain or an exit delay; a switch over whether a listener starts in this deployment; a `start` method that awaits a secret or a fetch before subscribing, a `stop` that closes its clients, whatever a signal handler calls. Each of those is an `excerpt` at the code that does it — what is loaded, from where, on what interval, what a failure there does to the process — and a `call` where it leaves the process, so the design builds the readiness the specification never states. A rule mounted for every route is claimed once, under `start`, and a handler surface names it by its key where a behaviour depends on it.
- A **handler surface** — a route, a job, a consumer, a command, an export — owns everything from its handler's invocation onward: validation, branches, the calls it makes, what it publishes or returns, how it acknowledges. Its hooks (`worker.on("failed")`) are its behaviour.
- A value `start` establishes and a handler uses — a client, a topic, a token, a cache — is named in the handler surface's requirement by its role (`the outbound stream`, `the upstream's token`) and, in the criterion or excerpt beside it, by the key or field the source spells (`Config.kafka.producer.topic`, `KAFKA_DEST_TOPIC`); its construction is `start`'s excerpt and is not re-claimed.
- A module several surfaces reach — a repository, a validator, a client wrapper — is claimed for what this seam's surfaces do with it, under their stems, never for itself. What it does for a surface of another seam is that seam's call to claim.

A boundary a dependency serves for the source — a plugin's health route, a library's metrics endpoint — has no handler of the source's own: it is `start`'s where the source states its path or its answer, and internal clients handed to a library's readiness helper, with no route or response contract of the source's own, are readiness wiring, an `excerpt` and a `call` for the design and no requirement. An inline value names no surface: find the surfaces it exposes as the caller would — what it registers, decorates, or exports — and claim each behaviour under that surface's noun.

## Claim kinds

This adapter emits from the closed enum:

| Kind | Required body field | When to emit |
|---|---|---|
| `requirement` | `statement` | One behavioural fact the code exhibits, stated as one present-tense sentence about the system. These are the claims deterministic reconciliation joins against documentation and intent. |
| `criterion` | `criterion` (free-form) | An acceptance boundary the source spells as a value of its own — one of the message's Boundaries — covering the requirement whose id it extends. |
| `excerpt` | `excerpt` (free-form) | A paragraph of focused context backing a requirement — the exact values, keys, defaults, and spans behind it — or carrying what the design holds where no requirement stands: startup readiness, credential retrieval and rotation, reference-table prefetch and refresh, retry policies, consumer acknowledgement, shutdown. |
| `call` | `callee` (free-form) | A call that leaves the process: outbound HTTP, a store, broker, cache, or identity-provider client, a metric or structured-log emission. |

**Emit no `type`.** The caller copies every `interface`, `type`, `enum`, and class the seam's modules export from the code, verbatim, into the source's document after this call answers; a `type` this call answers is dropped. Where a shape decides a behaviour — a union a branch switches on, a field a decorator maps to a wire name, a field the code makes optional that the declaration does not, a shape a module keeps to itself — state it in the `requirement` or the `excerpt` that needs it. A shape no declaration names — an inline structural type in a signature, a value assembled field by field, a response walked by path — has no declaration for the caller to copy, so the `excerpt` that needs it is its one home: spell it there, field by field, with each path and constant as the code spells it, and never as a `type`.

**Lift every behavioural fact into a `requirement`.** Only `requirement` claims reach reconciliation ([reconciliation.md](reconciliation.md)); `excerpt` and `call` claims reach synthesis as supporting context. Every behavioural fact worth a spec block — a validation rule, an error response, a side effect, a timing — is a `requirement` with a `statement`, anchored by its `path` and backed by detail claims.

### Requirements

Read each handler, and each module it reaches, for:

- **Inputs and validation** — which fields are read, which are required, and what happens when one is missing or malformed. A security check — path-traversal rejection, sanitisation, an authorisation check — is a validation like any other.
- **Branches and early returns** — every branch the caller can observe: a `return` inside an `if`, a `switch` arm, a ternary that changes the response. A branch left out is a behaviour the specification does not have.
- **Errors** — what is caught and what propagates; what is returned, thrown, or logged; whether execution continues. The extent of a `try` block is behaviour: a cache write inside it fails the way the fetch beside it fails. In a loop, whether one item's failure ends the operation or is recorded and the rest proceed. The plumbing around a failure is not: opening a transaction or a span, acknowledging or advancing a consumer in a `finally`, calling `next()`, catching and logging without rethrowing are `excerpt`s, and the requirement beside them is what the caller observes — the response returned, the event omitted, the next item or message still processed.
- **Side effects** — every write, publish, delete, and cache set, with its key or topic as constructed and the condition under which it happens. One that completes before the caller's response and one after are different behaviours.
- **Sequencing and timing** — `await` in sequence is sequential; `Promise.all` is parallel; a call without `await` completes after the response. Delays the caller observes and their placement (`sleep 5 s, then publish, repeated twice` is not `publish, sleep 5 s, publish`), the count of what is published, and a TTL a caller's later read turns on, with the values the source spells. A retry count, a backoff, a timeout, and a refresh interval are how the program reaches another system: they go in the `call` and the `excerpt`, and the requirement beside them is what the caller gets when the attempts are spent.
- **Transformations** — what a `map`, `filter`, or `reduce` keeps, drops, or computes, where the result is what the caller gets. A `switch` or lookup that maps one enumeration onto another — a source's event kind to a destination's, a code to a status — is a requirement at the switch, its arms the statement's values, and a pure function whose whole body is one computation is a requirement at its head. A helper is a requirement where a build must reproduce its arms, its formula, or the shape it constructs: a mapping function (`mapStatus`: codes `2, 3 → confirmed`, `4, 5 → shipped`, `9 → cancelled`), a pure arithmetic or date formula, a builder — a function whose whole body constructs the value it returns (an event, a message, a row): a requirement at its head stating the value it produces and what each field is read from, with the `excerpt` beside it carrying the shape as the wire carries it — every field at its exact path and nesting as the code spells it (`payload.timestamp`, `order.customer.id`, `shipment.weightKg`), the input each is read from, the constants put in (`kind`), and the parts left empty — since a builder stated by its field names alone leaves the shape it produces unstated. A helper folds into its caller's decision where it is only that decision's condition or a lookup one caller makes: a thin predicate (`isEligibleOrder`, handed to `find` or `some`, or called in a condition) or a single-caller lookup (`findRateByCode`) is that caller's requirement, which states what is compared and the tolerance allowed, with any table or constant the helper reads carried by the backing `criterion` or `excerpt`. A quantity a decision compares or a metric records — a delay, an age, a distance, a total — is stated as its formula over the inputs the code reads, with the clock, the units, and the zone it reads them in, and an input the code chooses by a condition or a position stated with the condition or the position (`now in seconds − (the created date at midnight in the configured timezone + the first change's actual time in seconds since midnight, the departure time where it has departed, else the arrival time where it has arrived)`), never as the list of what it is derived from, since a build given the inputs without the arithmetic invents the arithmetic and the choice. The same position goes into every statement that reads the element: a conversion that reads `changes[0]` throughout states `the first change's station` and `the first change's movement`, never `the station` or `each change's`, since a build told of a list reads every entry. A method whose whole body is one call through a package that leaves the process — a token provided, a table loaded, a secret read, a row fetched — is a `call` at that site with an `excerpt` for what it sends and reads; the requirement, where one stands, is what the caller gets from it or what its failure leaves them with (`An order whose items cannot be allocated is rejected with a 409 response`), claimed under the surface that runs it, and one whose whole body constructs a client is an `excerpt`.
- **Configuration** — the behaviour that depends on a `process.env` key or a constant, and whether the handler fails without it. The key is spelled exactly as the source spells it (`RATES_API_URL`, never a tidier name) in the criterion and the excerpt; the statement names it by what it configures, or by the key where the key is the domain's rather than the technology's, as [claims.md](claims.md) has it. The Boundaries list is where each is read and what it defaults to. When a behaviour reads a constant mapping or lookup table, the requirement states the rule and the filter the code applies to the table, and the `criterion` or `excerpt` backing it states the entries the code can reach — every entry where nothing narrows them, the active entries each with its mapped value where a filter does, the values themselves spelled in the claim (`"EU" → 3, "US" → 1, "APAC" → 7`; `12 → 51.50, -0.12`), since `as listed in configuration` states nothing and a build given the keys without their values invents the values.

**Stating a requirement.** One rule per statement, one sentence, present tense, about the system as the caller sees it: `Registration rejects an email that is not RFC-5322 valid with a 400 response.` A statement carries the value that is the rule — the status code, the limit, the duration, the count — and no more: a default, a hostname, a GUID, a URL template, a list of env keys is the backing `excerpt`'s to carry, named in the statement by its key. A handler that does five things is five requirements, not one sentence of five clauses. A statement names what the wire carries, never the HTTP client's holder of it: `if (response.data)` is `when the response carries a body`, `response.data.items` is `the body's items`, since a statement that says `when the response contains data` reaches the design as a field named `data` the wire never carried. A statement uses the domain's words, and an implementation's identifiers go to the `excerpt` and the `criterion`: a name is the domain's where a documentation source would spell it — `OVERDUE_DAYS`, `YYYY-MM-DD`, `invalid-email`, an `Order` — and the implementation's where only the code does — `Config.useTls`, `fetchRates`, `orderRow.createdAt`, `req.body.customerId` — so `An order older than OVERDUE_DAYS is flagged overdue` is a statement and `fetchRates sets orderRow.createdAt when Config.useTls` is not. Nothing the code does not exhibit: a handler that does not enforce uniqueness has no uniqueness requirement; the engine renders the gap, you do not fill it.

**Ids.** Ids follow [claims.md](claims.md): `<id>.<behaviour>`. The `<id>` is the surface line's — the stem alone, or the stem extended by what tells the surface apart — and the caller holds every `requirement` and `criterion` id to the stem it leads with; an id under another stem is refused and the answer put again. The `<behaviour>` is the source's own name for the behaviour: the function, branch, error type, metric, or key that exhibits it (`orders.place-order.reject-empty-lines`, `invoices.skip-paid`, `start.require-api-token`), less any technology name it carries — `orders.publish-placed` for a `publishPlacedToKafka` step — or the behaviour's role where little else is left (`start.credentials-before-clients`, not `start.confluent-secret-before-kafka`; `secrets.refuse-empty`, not `secrets.keyvault-empty`); the surface's id alone names the surface as a whole — what it does for the caller when nothing intervenes; a class method's behaviour extends the method's id (`money.add.currency-mismatch`). Never a paraphrase, a position, or a counter, and never the technology the surface is reached through: `invoices.reject-stale`, not `kafka-consumer.reject-stale`, as [claims.md](claims.md) has it. Two calls that name one requirement with reworded statements manufacture a conflict, so claim a behaviour under the surface whose caller observes it, and once. Two ids under one stem are two requirements the engine never merges, so one behaviour is one id, however many branches state it. An inline value names no stem: lead each id with the noun of the surface the value exposes it through.

**Criteria.** Code states behaviour, not acceptance. A `criterion` is an acceptance boundary the source spells as a value of its own — one the message's Boundaries list anchors: a named threshold constant (`MAX_ITEMS = 50`), a schema or validator definition, a pattern literal bound to a name, a configuration default the code falls back to (`PORT = Number(process.env.PORT ?? 3000)`) — one a documentation source could state verbatim. Its `path` is the boundary's anchor as listed; its id extends its requirement's; its `criterion` states the boundary as a checkable sentence with the value and its unit. A boundary that spells several values at once — an enumeration, a settings object, a schema with its defaults — is one criterion naming them all, under the requirement that reads it. An inline comparison in a guard (`items.length === 0`, `quantity < 1`, `state === "shipped"`) is behaviour: state it, with its value, in the `requirement` it belongs to and emit no criterion for it. The test is whether the value is declared once and referred to — listed under Boundaries — or written into the branch that uses it. A boundary no requirement rests on is no criterion. Requirements without criteria surface as `[unknown]` acceptance gaps in the spec — that is honest output, not a failure to fix by inventing criteria.

### Calls

A `call` is a call that leaves the process, at the site this seam's surface makes it, drawn from the message's Calls list: outbound HTTP (`fetch`, `axios`, an HTTP client); a store — SQL through `pg`, `mysql2`, `typeorm`, `prisma`, or `knex`; a managed table, document, or blob store through its SDK (`@azure/data-tables`, `mongodb`, `@azure/storage-blob`, `@aws-sdk/client-s3`); a cache (Redis, Memcached, an in-memory cache with a TTL); a message broker (Kafka, RabbitMQ, Service Bus, SQS); an identity provider (a token endpoint, `@azure/identity`); a WebSocket; and a metric, span, or structured-log emission that is part of the surface's contract. The list holds every call the modules make through a package, so read it as candidates: a validator's `parse`, a logger's `info`, a date or XML helper, a framework's response method does not leave the process and is no `call` — unless its emission is the surface's contract, as a metric or an audit log is. A call from one module of the tree to another is followed, not claimed: the store call inside a repository is the `call`; the handler's call to the repository is not. Every listed call that leaves the process is a `call` — a token fetched, a secret read, a reference table prefetched, a metric emitted, as much as the order written — claimed once at each of this seam's surfaces' sites, with its URL template, fields, timeout, retry rule, and refresh interval in the `call` and the `excerpt` beside it, since the design is built from them; a `requirement` stands beside it only where its result or its failure is part of what the caller observes.

- `path` at the call site; `callee` as the Calls list spells it — bare for a global (`fetch`), `<package>:<symbol>` for a package import (`axios:post`, `@azure/identity:getAzureToken`, `pg:Pool.query`), and `<file>:<symbol>` for a wrapper of the tree that makes the call when the list shows the site inside the wrapper (`src/lib/http.ts:HttpClient.post`); `synopsis` the operation and its target as constructed — the URL template, the topic, the entity and key columns, the metric name — and, where the code reads the response, the fields it reads by their path within the body after a `→` (`GET ${base}/rates?code={code} → rates[].amount`), the leaf included, since a requirement that says `the amounts from the rates array` leaves the field the amount sits in to be invented.
- Read from an outbound HTTP call site: the URL as constructed (base, path, and query, the exact template); method and headers with where each value comes from; the key or identifier the request sends and what it is read from; the response as the code deserialises and reads it — the fields read, each by its path within the response body (`await response.json()` assigned to `string[]`; `items[0].id`; `rates[].amount`), the client's own holder of the body stripped (`response.data` under `axios`, `res.body` under `superagent`, which are the client's and never the wire's), and never a broader declared interface; authentication and where the identity comes from; which statuses count as success and what the rest become; retries and timeouts as spelled. Best-effort and audit calls count: fire-and-forget is not unspecified.
- Read from a publish: the topic or queue as constructed (`${env}-${TOPIC}` is not `TOPIC`), the count from the loop bounds, the delay placement, the payload's shape as the wire carries it — the field paths and the constants, in the `excerpt` beside the call — and whether it changes between rounds, the key as constructed with the field it is read from (`order.customerId`) and the headers, and whether the caller's response waits for it.
- Read from a store access: the operation and the entity or table with its key columns (`SELECT orders WHERE (customer_id, placed_on)`); the key pattern and TTL for a cache (`get data:{id}; on miss fetch and set with TTL 3600s`). A managed table store reached over HTTP by its SDK is a store, not an outbound API.

What the caller observes through the call — what the response becomes, what is kept or answered when the attempts are spent — is the `requirement` the call backs; the timeout, the retry rule, the backoff, and the fallback are the `call`'s `synopsis` and the `excerpt`'s, and a `call` the caller observes nothing of — a credential obtained before the first handler runs, a table refreshed on a timer, a span opened — stands with its `excerpt` and no requirement.

### Excerpts

An `excerpt` is a paragraph of focused context — the validation rule, the error response, the side effect, the keys and defaults a requirement names — never a paste of the span: the anchor is the citation. One claim per concept; two overlapping excerpts of one handler are noise. An excerpt backs a requirement, or carries what the design holds where no requirement stands: how the program readies itself (what it loads or obtains before serving, from where, and what a failure there does to the process), how it rotates a credential, what it prefetches or refreshes and on what interval, its retry policies, how it acknowledges or advances a delivery, and how it shuts down — each at the code that does it, with the keys, intervals, and counts as spelled, so the lifecycle the specification never states still reaches `design.md`.

An excerpt is where a shape the code never declares is spelled. The one backing a builder or a publish carries the produced value as the wire carries it: each field at its exact path and nesting (`payload.timestamp`, `order.customer.id`, `shipment.weightKg`), the input it is read from, the constants put in (`kind`), and the parts left empty. The one backing a call whose response is read carries the fields read, each by its path within the body (`rates[].amount`, never `response.data.rates[].amount`, since the holder is the client's), and the key sent. The one backing a function whose signature spells an inline structural type carries that type, field by field. A design built from the specification lays the wire shape from these, so a path or a constant left out is one the build invents.

## Anchors and paths

Every claim from the tree carries a `path` anchor in the grammar of [claims.md](claims.md): relative under `$SOURCE_DIR`, the tightest range that bounds the cited text, never a whole file where a range exists, within the modules the message laid out or listed. Never under the [skip roots](claims.md#skip-roots) every adapter shares, nor under this adapter's own — `node_modules`, `vendor`, `target`, `.venv`, `dist`, `build` — nor in a `*.d.ts` file: the caller kept none of them, so none is laid, and a claim anchored in one is refused. A test file the message lists under Stated behaviours is read, never anchored by a `requirement` or a `criterion`: tests state expected behaviour; this adapter extracts the behaviour the production source exhibits, and anchors it there.

## Before answering

Check the Evidence against the source, not against a picture of the finished document:

- Every behaviour a caller observes through this seam's surfaces is a `requirement`: one rule, one present-tense sentence, an `id` led by its surface line's id and named for the code that exhibits it, a `path` at the span.
- No `requirement` states how the program readies itself, reaches another system, or recovers — a credential or secret loaded, checked, or rotated, a table prefetched or refreshed, a client constructed, a consumer subscribed, a retry or a timeout, a delivery acknowledged, a span opened, a handler installed for a signal or an uncaught error, a drain or an exit delay — even when a test states it directly, and each of those still stands as an `excerpt`, and as a `call` where it leaves the process, with its keys, intervals, and counts as spelled.
- No `statement` spells an identifier only the code does — an accessor, a field path, a method, a parameter, a constant that no documentation source would name; the domain's words carry the rule and the identifiers go to the `excerpt` and the `criterion`.
- Every branch, early return, error path, and side effect the caller can observe is stated.
- Every Boundary a requirement rests on is a `criterion` extending that requirement's id, at the anchor the list gives, with the value and its unit; every inline comparison stays in its requirement's statement; no Boundary is a criterion on its own.
- Every call that leaves the process is a `call` at its site with its target as constructed and its `callee` spelled as the Calls list spells it; no call between modules of the tree is one, and no listed helper, validator, or logger is one unless its emission is the surface's contract.
- No `type` is answered; a shape a behaviour turns on is in the statement or the excerpt that needs it, and a shape no declaration names — a value a builder or a publish produces, a response read by path, an inline structural type — is spelled in an excerpt with every field path and constant as the code spells it.
- Every key, constant, duration, count, and status code is spelled as the source spells it — the rule's value in the statement, the rest in the excerpt; a topic, queue, hostname, or group name as constructed is the `call`'s synopsis and the excerpt's.
- No `requirement` or `criterion` names a product, protocol, library, framework, or host — a broker, a web framework, a vault, an agent, an HTTP client — or is led by one, however the source spells it (`useConfluentKafkaConfig`, `KEYVAULT_HOST`, a package the modules import): what the system reaches is named by its role, and the technology is in the `call` and the `excerpt`. The caller holds every `requirement` and `criterion` to this, and one naming a technology in its id or its body comes back as a finding to restate.
- Every `path` names a module the message laid out or listed, with lines the file holds; nothing is anchored in a file the tree does not hold.
- Nothing is claimed the code does not exhibit — a stated behaviour the code confirms is claimed at the code where a caller of a surface observes it, one it does not hold is not; nothing for another seam's surface; nothing anchored in a test, a `.d.ts`, a dependency, build output, or the engine's own files.
- Every `requirement` has a `statement`; every `criterion` has a `criterion` and an id extending its requirement's; every id is dotted kebab-case.

## Failure modes

| Condition | Action |
| --------- | ------ |
| The seam reaches no in-scope production source — a handler that is a stub, an export of types alone | Return `claims: []`; the engine preserves the gap rather than guessing. |
| Production source uses an out-of-scope framework only | Emit any in-scope claims; the gap surfaces as `[unknown]` requirements in the spec. |
