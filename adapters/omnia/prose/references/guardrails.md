# Guardrails

What a module of the [layout](layout.md) never does, and what it does instead. The program is a WebAssembly component: it holds no process, no file system, no socket, and no clock of its own, and it lives one request or one delivery at a time. Every effect goes through a capability of the provider, as the [handlers](handlers.md) reach them.

## The lints are the boundary

The workspace's lints carry the host boundary, and the loop's first check runs them over your crate. `clippy.toml` names what a module never reaches on its own — the environment, the file system, the network, a thread or a task, the clock, the process, state kept across calls, a file compiled in — and each entry's `reason` names the capability to reach instead. The lints are `forbid`, so no module lifts one with an `allow` or an `expect`, and `allow_attributes` is forbidden beside them: a lint failure in your crate names the capability, and the repair is that capability, never an attribute. A stem's manifest inherits them through `[lints]` with `workspace = true`, which the adapter holds every stem to.

What the lints cannot see, since it arrives as a crate rather than a path, follows the same rule, and the guest check of the loop refuses most of it: a module reaches an upstream through `HttpRequest::fetch` with an `http::Request`, never `reqwest`, `hyper`, or `ureq`; a database through `TableStore` for SQL and `DocumentStore` for documents, never `sqlx`, `postgres`, `rusqlite`, or `mongodb`; a broker through `Publish::send` to a topic of `common::topic`, with a handler registered in the part's `topics(..)` to consume one, never `rdkafka`, `lapin`, or `redis`; a WebSocket through `Broadcast::send`; a credential through `Identity::access_token`; the time through `chrono::Utc::now()`, since the design's timestamps are `chrono` types serialised as RFC 3339; an id through `uuid::Uuid::new_v4()`; and a trace through `tracing::info!` and its siblings, which `omnia_sdk` re-exports, never `println!` or `dbg!`. A background job is a route or a topic the host calls, and `tokio` is a dev-dependency for the tests alone.

A crate compiles for `wasm32-wasip2` when it is pure Rust and reaches none of that: `serde`, `serde_json`, `chrono`, `uuid`, and `thiserror` are pinned in the root manifest for that reason. A crate with a C dependency (`openssl`, `native-tls`, `rusqlite`), one that reaches the system (`reqwest`, `tokio` as a runtime), or one that needs a build script to probe the host fails the guest check of the loop, and the module that named it is the one to change.

## The host is not simulated

The source a specification was read from may have been a process: a server that listened, a worker that polled a queue, a scheduler that ticked, a client that connected at start-up and reconnected on loss, a shutdown that drained. The component is none of these, and the host does each for it, so a requirement that states one is satisfied by the host or by nothing in the tree, never by code that imitates the mechanism. What each mechanism the source named becomes here, row by row, is the [translation](translation.md):

- No `crates/start/` crate, no `main`, no `start`, `stop`, `run`, `listen`, `serve`, `bootstrap`, or `shutdown` function, no `Main`, `App`, `Server`, or `Application` struct, and no struct holding a `started`, `running`, `connected`, or `ready` flag: the seed and the host are the program's start, there is no process to be in a state, and the host instantiates the component for each request. The adapter refuses any file under `crates/start/`, and under any stem's `src/` it names each such function or struct with its line and refuses the report or the verdict until the module is removed, with its `pub mod` line and its test, never renamed.
- No loop that polls or retries, no subscription set up in a handler, no reconnection, no heartbeat, no graceful stop: a topic is consumed through the part's `topics(..)`, a connection is the host's to keep, and a call that fails is carried as the classified error for the host to redeliver or the caller to retry. The actions a loop repeated run once, back to back; a loop that never breaks fails the lints.
- No route added to stand for a lifecycle — `GET /ready`, `POST /start`, a probe that reports a flag — unless a requirement states the route itself; a route answering a requirement that states none is a surface the specification does not hold.
- No flag machine: the lifecycle moved into data is the lifecycle still. A `StateStore` key that records a step done (`STARTED_KEY`, `INITIALIZED_KEY`, `LOADED_KEY`, a `b"1"` written to say so), a guard that orders one handler after another by reading such a key, a stored stop request, exit delay, or restart intent, and a handler whose only effect is such a write are each the process simulated. A step the source took once at start is a read at the moment of use; a step it took on a signal is nothing.
- A requirement of this kind is covered where the host satisfies it as stated — a request is answered, a delivery is consumed — and left out of `covered` where the host satisfies it by needing nothing, never reported covered over a stub. The report says what the tree holds.

## What `start` becomes

The `start` stem is where a specification read from a process keeps what that process did at start-up: read its settings, build its clients, connect, listen, prefetch its tables, wire its monitoring, catch its signals. The seed's entry, provider, routers, and shared `common` crate, together with the host, are `start`: no crate `crates/start/` is ever written, and the adapter refuses any file under `crates/start/`. Each start-up responsibility is one row below, and the row says what a slice under `start` writes for it and how its report reads — the slice `start` itself, or one the plan cut from the stem by what the process did, `start-prefetch`, `start-credentials`, `start-bootstrap`, each held to the same rows:

| The source's `start` did | The slice writes | The requirement is |
| --- | --- | --- |
| read its configuration — environment variables, a settings file, a config object handed to every component | nothing of its own: a setting a handler reads is a `pub(crate) const` of the part that reads it, named for what it is and read through `Config::get` at the moment of use; no constant for a broker, vault, or agent setting, no settings struct, no catalog, no load at start | covered by the reads where a handler reads the setting; left uncovered where the setting configured the mechanism alone |
| held a credential or a secret retriever — a vault client, a key-vault reader, a token exchanged at start and refreshed | nothing of its own: the handler that needs the value reads it through `Config::get` or `Identity::access_token` where it uses it; no cache, no refresh, no watcher, no retry around the read | covered where a handler reads it; left uncovered where the requirement states the retriever, the validation at start, the cache, or the refresh itself |
| constructed a client to an upstream and handed it on — an API client, a gateway, a store connection | nothing: the stem that calls the upstream owns the call, as a function over `HttpRequest::fetch` or the store capability, constructed nowhere | that stem's; `start` covers nothing of it |
| prefetched a reference table or a mapping, to be read by the handlers and refreshed on a schedule | nothing: the table is cache-aside over `StateStore` in the stem whose handlers read it, as [the translation](translation.md#a-reference-table) spells it — one `pub async fn` of that stem, one key, a miss fetched and stored with a TTL for the refresh and the table answered, never an empty one — and `start` writes nothing of it | left uncovered: the load at start is the mechanism, and the table's load and lookup are the reading stem's requirements, covered by the slice that writes the function |
| listened, bound a port, served, connected to a broker, subscribed — or read a deployment-slot or enablement flag to decide whether to | nothing: the host answers HTTP and deliveries through the two root lists, and a part's `topics(..)` registers its topic unconditionally; no setting for the flag and no check of it | covered, by the seed and the host, as stated; a requirement whose statement is the flag left uncovered |
| initialised monitoring — an APM agent, a metrics exporter, a logger, a tracer | nothing: the host collects what `tracing` emits | covered, where the requirement states that the program is observed; left uncovered where it states the agent or the exporter |
| handled a signal, drained, stopped | nothing | left uncovered |
| ran a periodic job — a poller, a scheduler, a cron | nothing, unless a requirement states a route or a topic the host calls for it, which is that requirement's handler | left uncovered otherwise |
| declared a lifecycle type — a `Main`, an `App` with a `started` flag, a `Server` struct with `start` and `stop` | nothing: the type is not declared, whatever the design calls it, and no `StateStore` key stands in for its flags | left uncovered |
| answered a health or readiness route a requirement states by method and path | that route in its own stem's crate (`crates/health/`), never under `crates/start/` | covered by the slice that owns that stem |
| enforced a rule every route obeys — authentication, a body limit, a request log | a `pub fn` of the stem that owns the rule, called at the top of the handlers it guards | covered, with the handlers' tests |

So a slice under `start` never writes `crates/start/` and never adds `start` to `Cargo.toml`: it covers the rows that say so over the seed and the host, leaving credential retrievers, rotation watchers, client construction, table prefetch, signals, periodic jobs, and lifecycle types out of `covered` with no module written, and a setting it names is declared by the part that reads it, in that part's slice.

## Errors

- A handler answers a classified error or `Ok`, never a panic: no `unwrap`, `expect`, `panic!`, `todo!`, `unreachable!`, slice or map indexing on request data, or arithmetic that can overflow on it. A panic is a trapped instance and a `500` the program did not choose.
- The class is the requirement's: a request the specification refuses is `bad_request!`, a thing it says does not exist is `not_found!`, an upstream that fails is `bad_gateway!`, and `server_error!` is what the program itself cannot do — a stored value that no longer parses, a serialisation that fails.
- A failure the handler cannot classify is carried with `?` as it is, never swallowed into a default, an empty list, or an `Ok`.
- `unsafe` has no place in a module, and a module declares no `build.rs`, no procedural macro, and no `#[no_mangle]`; the workspace denies `unsafe_code`.

## Secrets

- No credential is written into the tree: no key, token, password, connection string, or `.env` file, and no test fixture holding one. A value the program needs is a `Config::get` at the moment of use, under a constant the part declares and names for what it is (`RATES_URL`, `PAYMENTS_API_KEY`), and a test hands a placeholder through `MapConfig`.
- Nothing of what a handler reads from the host is logged or answered back unless the requirement asks for it: a token fetched to call an upstream goes into that request's header and nowhere else.

## The files a slice never edits

- The seed outside its lists, as the [layout](layout.md) states them: `src/lib.rs`, `tests/routes.rs`, `tests/messaging.rs`, `examples/runtime.rs`, `crates/common/Cargo.toml`, `crates/common/src/lib.rs`, `crates/common/src/config.rs`, `clippy.toml`, the toolchain and tooling files, `supply-chain/`, and `.github/`; the static text of the root `Cargo.toml`, the two root lists, the topic table, a stem's entry, and a stem's manifest around their lists, the pins, the `host` feature, the target tables, and the dev-dependencies among it. A pinned version is the tree's, and a crate the pins lack is named with its version in the stem's manifest alone, never as a `git` or `registry` source.
- `Cargo.lock`, which cargo writes.
- Another slice's module or test file, and anything under `.emery/` or `target/`.
