# Translation

How a requirement that names a mechanism lands in the [layout](layout.md). The specification was read from a source that ran somewhere — on a broker, behind a web server, against a vault, under an APM agent — and a requirement, a scenario, or a design type may still spell that platform's parts: the consumer, the producer, the client, the agent, the group, the timer. The guest is a WebAssembly component on the omnia host, and the host plays every one of those parts through a capability of the provider, as the [handlers](handlers.md) reach them, so the specification's technology is never the tree's.

## The rule

- The specification decides what the program does; this layout decides how. A requirement that states a mechanism is read for the behaviour behind it — what arrives, what is checked, what is answered or published, what fails — and that behaviour is implemented through the capability that plays the role. The mechanism's own parts are laid nowhere: no crate for the product, no type named for it, no setting for its address, no state standing in for its session.
- The design's `apis` section names each system the source reached by its role, with the technology beside it. The role is what a module reaches — a stream through `Publish` and a part's `topics(..)`, a store through `StateStore`, `TableStore`, `DocumentStore`, or `BlobStore`, an upstream through `HttpRequest`, an identity provider through `Identity`, a setting through `Config` — and the technology is what the deployment binds behind the host, which no line of the tree names.
- A requirement that states behaviour and mechanism together is covered by the behaviour: `the consumer in group X rejects an update older than the last seen` is covered once the handler its part registers for the topic rejects such an update, whatever the group was.
- A requirement whose whole statement is the mechanism — the broker's addresses, the consumer group, the transport security, the client's construction, the agent's initialisation, the delay between two sends — states nothing the tree can hold. It is left out of `covered`, with no stub, no constant, and no comment standing for it, as [build.md](../build.md)'s report rule has it. A design type the design labels `(mechanism)` — a client, a connection, a settings bag, a retriever, a lifecycle — is laid by no slice, and the plan assigns its key to none; the domain types beside it, the payloads, the events, the records, each assigned to one slice, are laid as the handlers reference spells them.
- A setting is kept where it configures behaviour and dropped where it configured the mechanism: `OVERDUE_DAYS` is a `pub(crate) const` of the part that applies the rule, read where it applies; `KAFKA_HOSTS`, `KAFKA_GROUP_ID`, `APM_SERVICE_NAME`, `PORT`, and `VAULT_URL` are the host's and get no constant. A key the source read a topic from is no setting here either: the topic is a constant of the topic table, qualified by `config::topic` as every topic is.
- A setting is what the deployment supplies and may vary between deployments: an upstream's endpoint, an identity or a credential's key, a bound an operator tunes, each a `pub(crate) const` of the part that reads it, its value its name. A value the specification states as a value is not a setting: a mapping from one code to another, a format string, a timezone or a locale, a threshold a scenario spells out is a `const` of the module that reads it, spelled as the scenario states it, with no setting and no default standing for it; and a setting that configured the mechanism alone — the broker's, the vault's, the agent's — gets none either.

| an APM agent, a transaction or span opened and closed, a metric counter, an error notice, a status line logged | a `tracing` event with the fields the requirement names; a metric a `tracing` event the host's metrics layer reads by its field's prefix | `tracing::info!`, `warn!`, or `error!` at the point the requirement states; a counter `tracing::info!(monotonic_counter.<name> = 1)`, a measurement `tracing::info!(histogram.<name> = <value>)`, a level `tracing::info!(gauge.<name> = <value>)`, `<name>` in snake_case under the stem (`orders.rejected_expired`) with the agent's prefix dropped; no agent, no exporter crate, no `StateStore` key standing for a span or a count | yes where the requirement states what is observed and with what fields; no where it states the agent or the exporter |
| a web server, a port, listening, framework middleware run for every route | the host answers HTTP through the route list; a rule every route obeys is a `pub fn` of the stem that owns it | nothing for the server; the `pub fn` and the calls at the top of the handlers it guards for the rule | as [what `start` becomes](guardrails.md) says |
| a health or status route stated by method and path | a route | the route in the stem that states it, answering what the requirement says, never a lifecycle's flag | yes |
| a WebSocket push to connected clients | `Broadcast::send` | the `send` in the handler; a test reads `provider.broadcast.broadcasts()` | yes |
| a design type the design labels `(mechanism)` — a client, a connection, a settings struct, a retriever, a `Main` or an `App` | nothing | no struct, under no name: the plan assigns a mechanism type to no slice, and a slice whose requirements mention one reaches the capability that plays its role; its setting fields become settings of the parts whose handlers read them | a type is no requirement; a requirement stating its construction is left out |
| a design type without the label — a payload, an event, a record, a result | a `pub` struct of the slice the plan assigns the key to, in the wire shape the design's `apis` section spells | the struct as the [handlers](handlers.md) reference lays it, `serde(rename)` where the wire's field names are not Rust's | a type is no requirement |

## A reference table

A stem that reads a table the source loaded at start and refreshed on a schedule lays one function the handlers call at the moment of use, and nothing of the schedule:

```rust
use common::config;
use omnia_sdk::{Config, HttpRequest, StateStore, server_error};

/// How long a loaded table serves before it is fetched again.
const TTL_SECS: u64 = 10 * 60;

/// The state-store key of the rate table.
const RATES: &str = "pricing/rates";

/// The rate table, fetched when the store holds none or the held one has aged out.
///
/// # Errors
///
/// `bad_gateway` when the upstream cannot be reached; `server_error` when a held table does not read back.
pub async fn rates<P>(provider: &P) -> omnia_sdk::Result<Vec<CurrencyRate>>
where
    P: Config + HttpRequest + StateStore,
{
    if let Some(bytes) = StateStore::get(provider, RATES).await? {
        return serde_json::from_slice(&bytes).map_err(|error| server_error!("rate table: {error}"));
    }
    let rates = fetch_rates(provider).await?;
    let bytes = serde_json::to_vec(&rates).map_err(|error| server_error!("rate table: {error}"))?;
    StateStore::set(provider, RATES, &bytes, Some(TTL_SECS)).await?;
    Ok(rates)
}
```

`fetch_rates` is the upstream call of the row above it, over `HttpRequest::fetch`, failing as `bad_gateway!`. A miss — `StateStore::get` answering `Ok(None)` — fetches, stores, and answers the table it fetched, never an empty one: a function that answers `Vec::new()` on a miss has laid the cache and lost the table. There is no key holding when the next fetch is due, no handler that loads the table, no retry around the fetch, and no flag that the first load ran: a failure is the handler's error, and the host redelivers or the caller retries. The function is laid once, by the slice whose requirements state the table's use, in that stem's crate, and `start` never lays one under `crates/start/`, whatever its requirements state of the prefetch: a loader laid first under `start` is a second one the moment the reading stem lays its own, so `start` lays nothing of the table and covers nothing of it, as [what `start` becomes](guardrails.md) says.

## A worked example

A stem `shipments` whose requirements were read from a consumer: `the Kafka consumer on topic KAFKA_SRC_TOPIC in group KAFKA_GROUP_ID parses each XML message into a ShipmentNotice`, `a notice whose timestamp precedes the last one seen for its shipment is rejected and the notice counter incremented`, `each remaining notice is converted and sent to the producer's topic with the shipment id as the key, with DELAY_MS between sends`, and the design's `apis` section names an inbound stream and an outbound stream, both over Kafka, with the suffixes `shipment-notices.v1` and `shipments-dispatched.v1`.

The slice lays two constants in the topic table, `SHIPMENT_NOTICES` and `SHIPMENTS_DISPATCHED`; one `.route(..)` in its part's `topics(..)`, `messaging::consume_with(on_notice, decode)`, the decoder reading the XML payload into the design's `ShipmentNotice` through `quick_xml::de::from_str`; the part's `consuming::topics,` entry in the stem's topics list; and the handler, bounded on `StateStore + Publish + Config`, which reads the last timestamp seen under `shipments/<shipment id>`, rejects an older notice with a `tracing::warn!` naming the shipment and returns `Err(bad_request!("outdated", ..))`, stores the newer one, converts it, and publishes it once through `Publish::send` under `config::topic(provider, topic::SHIPMENTS_DISPATCHED)` with the shipment id in the `key` header. The tests deliver an XML payload under `test-shipment-notices.v1` through `shipments::topics(Router::new(Client::new("test", provider.clone())), "test")` over a `Provider` whose `storage` holds the earlier timestamp, and read `publish.sent()` for the one message and its key.

The report covers the first requirement by the parse, whatever its group and its setting said, the second by the rejection, and the third by the conversion and the publication, the delay laid nowhere. A requirement whose whole statement is the delay, or the counter as the agent's metric rather than what is observed, is left out: nothing in the tree holds it, and the operator reads the gap in the plan rather than a stub in a module.

When a consumer stem is split across two slices — an earlier stage slice (`processing.rs`) that parses, validates, filters, and converts an XML notice, and a later entry slice (`delivery.rs`) that consumes the topic, resolves upstream reference data and carrier allocations, and publishes the outbound event — keep the two modules one pipeline:

1. **Same-stem composition and stage return types:** `delivery.rs` imports and calls `crate::processing::*` for the XML types, deserialization, validation, filter, and event conversion. Stage validation and conversion functions return `omnia_sdk::Result<T>` built with `bad_request!`, `not_found!`, `bad_gateway!`, or `server_error!` — never custom error enums or `Option<T>` that swallow the rejection reason into `Ok(())` — and the topic handler propagates stage and upstream errors with `?`. Never write a second XML parser or duplicate types in `delivery.rs`; if integrating `delivery.rs` exposes a defect in `processing.rs`, fix `processing.rs` through `edit_files`. The entry's `consume_with` decoder reads `&delivery.payload` straight into the root wire type the stage declared — `fn decode(delivery: &Delivery) -> Result<Envelope, DecodeError>` over `quick_xml::de::from_slice`, or over the stage's own `pub fn parse_notice(&[u8])` — never into an intermediate carrier of the raw payload (`struct InboundBody { pub xml: String }`) the handler parses again, and the stage module holds one parse, one validation, and one conversion, each a `pub fn`, never a chain of wrappers (`accept_notice`, `process_notice`, `deserialize_and_validate`) each calling the next.
2. **Root XML element in `quick_xml::de`:** The struct passed to `quick_xml::de::from_str::<T>` or `from_slice::<T>` represents the root XML element itself (`<Envelope>`), with its direct child element as its field (`#[serde(rename = "ShipmentNotice")] pub notice: Option<ShipmentNotice>`), and `ShipmentNotice` carries its child elements (`#[serde(rename = "primaryRef", default)] pub primary_ref: String`, `#[serde(rename = "secondaryRef", default)] pub secondary_ref: String`, `#[serde(rename = "issueDate", default)] pub issue_date: String`, and `#[serde(rename = "leg", default)] pub legs: Vec<Leg>`). Never wrap `T` in an outer struct renaming the root tag (`#[serde(rename = "Envelope")]`), which makes `quick_xml` expect `<Outer><Envelope>...` and fail on every valid payload.
3. **Sequential guard precedence and delay bounds:** When a specification or design selects a value from a primary branch when a flag holds and a secondary branch otherwise, and then validates the selected value (`if has_departed { departure_secs } else if has_arrived { arrival_secs }`, then reject `<= 0` as `bad_request!("no_update", ...)`), evaluate the branches in strict `if / else if` order and validate the chosen value afterwards — never folding `> 0` into the branch condition so a primary branch with `<= 0` falls back to the secondary branch. Compute timeliness bounds (`delay = now_unix - event_time`, refused as `bad_request!("outdated", ...)` when `delay > max_delay` and `bad_request!("wrong_time", ...)` when `delay < min_delay`) with the exact sign and reason codes the specification states.
4. **In-memory filtering before cache-aside or HTTP I/O, and mapped code filters:** Check in-memory domain filters (such as whether a leg's movement kind is tracked or whether a facility ID or its mapped code in a constant lookup table belongs to the active filter set) *before* calling a cache-aside `StateStore` / `HttpRequest` loader, so filtered-out deliveries return early without triggering cold-cache HTTP calls. When a filter lists source IDs (`"1,4,9"`) and a lookup table maps source IDs to target codes (`1 -> "WH-101"`), map both sides to the same code space before comparing rather than comparing a mapped code against unmapped IDs. When the payload carries a list of entries where the first is the event reported and the rest are its context — the legs of a notice, `legs[0]` the movement that happened and the later legs its schedule — the filter reads the first entry's kind alone, whatever `legs.len()` is, and never keeps a multi-entry payload because a later leg's kind is tracked; only a scenario stating that a multi-entry payload whose first leg is untracked is kept makes it otherwise.
5. **Upstream query keys and HTTP response shapes:** Query upstream endpoints with the identifier the specification states (`externalRefId` set to the first non-empty of `primary_ref` and `secondary_ref`, never an internal registration number), and deserialize top-level JSON array responses directly into `Vec<Facility>` and root JSON object responses into a struct with the root fields (`struct AllocationsResponse { #[serde(default)] pub all: Vec<CarrierAllocation> }`), never wrapped in a `data` field. Propagate the upstream's failures as the table's upstream row has them: a fetch that errors, a status that is not success, or a body that does not parse is `Err(bad_gateway!(..))` through the helper and the handler with `?`, never an empty `Vec` answered in its place; and an entry the delivery names that the fetched table lacks, once the in-memory filter has admitted the delivery — a facility the filter lists, a carrier the notice names — is a failure of the lookup, `Err(not_found!(..))` or `Err(bad_gateway!(..))` as the specification classifies it, never the delivery dropped as a filtered no-op, since the filter decided what is in scope before the fetch and a table lacking an in-scope entry is the table's fault, not the delivery's; a scenario of the slice's specification that states the `Ok` outcome in so many words, and that alone, makes it otherwise.
6. **Outbound wire shape, optional fallback fields, and numeric types:** Serialize the outbound event in the exact nested wire shape the design's `apis` section spells (`#[serde(rename_all = "camelCase")]`). Populate only the fields the source's builder sets: when a field on an outbound type is only read as a fallback in a publish-key expression (`external_id || remote_name`) and never assigned by the builder, type it as `Option<String>` with `#[serde(skip_serializing_if = "Option::is_none")]` and leave it `None`. Type integer constants (`0`) as integer types (`i64` or `u64`), never `f64` (`0.0`), and declare topic constants with the exact suffixes the design's `apis` section spells (`"shipment-notices.v1"` and `"shipments-dispatched.v1"`).

## What it is not

- A `KafkaConsumerSettings`, a `BrokerConfig`, a `ConsumerGroup`, a `Producer` struct, or a module that connects: the host subscribes and publishes, and the parts' `topics(..)` are the whole of the subscription.
- A `StateStore` key standing for a span, a transaction, or an agent's counter (`set("apm/transaction", ..)`): a trace is a `tracing` event, and a count the host does not keep is not kept.
- A topic suffix composed at run time from an environment prefix and a dormant flag: the environment is `config::topic`'s, the dormant switch is laid nowhere, and the constant is the suffix as the design states it.
- A setting, a `Config::get`, or a check in `topics(..)` or a handler for a flag that decided whether the source's consumer or listener ran — a deployment slot, an enablement switch: the host runs every handler the parts register, and a requirement whose statement is the flag is left out of `covered`.
- A struct carrying the raw payload (`struct InboundBody { pub xml: String }`) between `consume_with`'s decoder and the handler, or a chain of stage wrappers (`accept_*`, `process_*`, `deserialize_and_validate`) each calling the next: the decoder reads the payload into the wire's root type once, and the stage holds one parse, one validation, and one conversion.
- A helper that answers an upstream's failure as `Ok(Vec::new())` or `Ok(None)` because the source's client wrapper did: the failure is `Err(bad_gateway!(..))` out of the handler, and a scenario alone, stating the empty answer, makes it otherwise.
- A `start` module that constructs the clients the source built, reads the settings into a struct, loads a table another stem reads, or holds the program's state, which [what `start` becomes](guardrails.md) lays nothing for.
- A struct wrapping an upstream's response in the `data` or `body` field the source's HTTP client held it in: the wire carries the body alone, and the struct is the body's shape.
- An event loop over an XML or CSV reader, matching each element or record by hand: the payload is read through the format's `serde` reader into a type deriving `Deserialize`, and a repeated element is a `Vec` field.
- A setting for a value the specification states — a code mapping, a format string, a timezone, a threshold a scenario spells — which is a `const` of the module that reads it, as the scenario states it.
- A `#![allow(..)]` at the head of a module or a crate, silencing the workspace's lints over code the translation left as the source had it: the lints are the tree's, a module that needs them off is laid wrong, and the verify refuses it with the file named.
