# target.build

Build one slice of the plan into the lent project tree as an omnia guest in Rust, check it lints, its tests pass, and it compiles for `wasm32-wasip2`, and report what you covered and wrote.

## Inputs

- `$WORKSPACE` — the project tree, lent writable, sitting on the commit the brief names. Read it through the workspace tools; write it through this call's two tools alone: `edit_files` changes within a file the tree holds, each edit the one place its `find` matches and the text to put there; `write_files` writes a file whole, one or more per call, each created or replaced at a `/`-separated path relative to `$WORKSPACE`, and removes a file through the same call's `delete`. Your slice's files are in the tree before you start, so your work is `edit_files` over them; `write_files` is for a file the brief names as not scaffolded, and for a file the loop below has you rewrite whole. The shell runs the checks below in `$WORKSPACE` and nothing else: a file the shell writes, through a redirect, a heredoc, `cp`, or a script, is outside the tools and is not yours. Nothing outside `$WORKSPACE` is reachable.
- **The slice's plan entry** — its id, name, requirements, the design types it owns, and the slices it depends on.
- **The specification, cut to the slice** — the requirements to implement, each with its acceptance scenarios.
- **The design, whole** — the types and sections every slice shares.
- **What the adapter scaffolded for this slice before this turn** — per stem of the slice: the files it scaffolded or found held, the lines it added to the lists, and the markers to fill, in order.

Build this slice completely in one pass. Other slices of the wave are building beside you from the same commit; what you write merges with theirs under the rules the [layout](references/layout.md) states, so keep to its shape.

## What to write

The [layout](references/layout.md) is the one shape every slice follows: the root package is the guest, `common` holds what every stem shares, and each stem is a crate under `crates/` whose entry composes its parts' routes and topics into one router of each kind, which the root lists merge. The adapter scaffolded your slice's place in it before this turn, from the requirements and types the slice carries: the stem's crate, `crates/<stem>/`, with its manifest and entry where the tree lacked them; your part, `crates/<stem>/src/<part>.rs`, with a path constant and a `.route(..)` per route your requirements state, a handler per route over an empty input and output struct, a `pub fn` per requirement stating no route, and an empty `pub struct` per design type you own; your tests, `crates/<stem>/tests/<part>.rs`, one ignored test per acceptance scenario; and your lines in every list, the stem's four at the root and the part's in the entry. Each place your code goes is a marker, `todo!("REQ-.. <subject>: ..")` in a body or `{}` on a struct, and the brief lists every marker with the file it stands in. Fill them, in the brief's order:

- **The design types you own**: `pub struct <Type> {}` becomes the type the signature in its doc spells, as the [handlers](references/handlers.md) reference declares a design type — every field documented, the wire's names kept through `#[serde(rename = "..")]` — less a type that is a client, a connection, a settings struct, or a lifecycle, which the [translation](references/translation.md) writes nothing for: leave such a struct empty and say nothing more of it.
- **The handlers**, as the [handlers](references/handlers.md) reference spells them: fill `<Name>Input` with one field per path parameter, which the adapter scaffolded, query parameter, or body field, and `<Name>Output` with the response's fields; write the body in place of its `todo!`, and drop the `let _ = (input, context);` line above it. The host is reached through `context.provider()` alone, a setting under a `pub(crate) const` of your part whose value is its name — the identity `Identity::access_token` takes among them — a topic published under a constant of `common::topic` qualified through `config::topic`, and every failure — a fetch that errors, a status that is not success, a body that does not parse — a classified `omnia_sdk::Error` propagated with `?` rather than caught and answered as `Ok(())` or an empty collection, whatever the source's client wrapper answered its `.catch` with. One handler serves every requirement its marker names, since two requirements stating one method and path are one route. The adapter read each route from the `METHOD /path` its requirement states, in the statement or a scenario's `when`; where it read one wrong — a route misspelled, a path it should have joined — the constant, the `.route(..)`, and the handler are yours to put right in your module.
- **A requirement stating no route** is a `pub fn` with a marker: a stage of a pipeline, a rule every route obeys, a behaviour another part calls. Give it the signature the behaviour needs and write the body, returning `omnia_sdk::Result<T>` built with `bad_request!`, `not_found!`, `bad_gateway!`, or `server_error!`, never a custom validation error enum or an `Option<T>` that swallows a rejection reason, and add no route to give it a surface. Where the requirement consumes a topic — the design's `## APIs and integrations` lists an inbound stream whose bullet cites it or another requirement of your stem, or whose deliveries its scenario's `when` describes — the function is that stream's handler instead: a `pub(crate) async fn(input, context) -> omnia_sdk::Result<()>` registered through a `pub(crate) fn topics(router, env)` you add to your part, `router.route(config::topic_for(env, topic::<NAME>), messaging::consume(<handler>))`, its constant at the end of `crates/common/src/topic.rs` where no slice has declared it, and one `<part>::topics,` entry at the end of the array in the entry's `topics(..)`; the registration itself is never a requirement, since the host registers and acknowledges. A topic you publish to and no requirement of yours consumes is its constant in the topic table alone, named from your handler through `config::topic`. The slice that ends a pipeline — the one that publishes, or that `depends-on` the stem's other slices — registers the consumer where no part of the stem has, the handler calling the earlier parts' functions in the pipeline's order; a part that publishes in a stem no route or topic reaches, and no other stem calls, is a finding on your report, since nothing ever runs it.
- **The tests**, `crates/<stem>/tests/<part>.rs`: each scenario is a `#[tokio::test]` named by it, under `#[ignore = "<id> <scenario>: unfilled"]` over a `todo!`. Fill it as [testing](references/testing.md) spells it — the arrangement over the doubles of `omnia_test::guest`, the request through your stem's `router()` and `oneshot` or the delivery through its `topics(..)`, the assertions the scenario states — and remove its `#[ignore = ..]` line. A scenario the specification gives you is a test; invent none, and delete none: a scenario you cannot yet satisfy keeps its ignored test as scaffolded, and its requirement stays out of `covered`. A service the tree does not run is a double handed to the provider, never a live connection.
- **The lists** are filled: the stem's line in each root list, the part's `pub mod` line and `routes()` entry in the entry, all added by the adapter where the brief says `added`, held where an earlier slice added them. What the adapter does not derive is yours to add through `edit_files`, at the end of its list where the layout's table says: a constant in the topic table, a `<part>::topics,` entry, and one `<crate>.workspace = true` line at the end of your stem's `[dependencies]` for each crate your code uses beyond the six the manifest holds, a crate the root manifest does not pin carrying its version instead. Where the brief says a line was not added — the file lacked its anchor — add that line yourself. Change no other line: a line you find in a list is not yours to rewrite, reorder, or fold your own into, since the merge keeps every form it is given and the verify then has two. Write no crate: your stem's is scaffolded, one word whatever its hyphens (`crates/order-items/` for `order-items`), and a crate the turn writes under any other name is a finding on your report. Your wiring is those lines and nothing else: no `mount`, no router of your own beyond your part's `routes()`, no change to `src/lib.rs`, and no edit to another stem's crate to be reached; the host runs a stem through its `routes()` and `topics(..)` alone.
- **The seed**, every file outside `crates/<stem>/` beside `Cargo.lock`, is in the tree before you start: the adapter scaffolded the exemplar's guest template when the repository was initialised, byte for byte, so no slice writes or reports a seed file; read one in the tree where you need its text. The root `Cargo.toml` is held to the seed outside its two lists when you report: a pin, a lint, or a feature changed there is a finding with the lines named, and a check that passed through the change is no check at all.
- **The `start` stem**, where your slice is under it — the slice `start` itself, or one the plan cut from it, `start-prefetch`, `start-credentials`, `start-bootstrap`: the seed and the host are the program's start, so the adapter scaffolded nothing for a `start` requirement, and **never write `crates/start/`** or add `start` to `Cargo.toml`; the adapter refuses a report over any file under `crates/start/`. Everything the source did at start — read its settings, load or watch its credentials, build and hand on its clients, connect, listen, prefetch a table, watch itself, catch its signals, keep a lifecycle type — translates by the table in [what `start` becomes](references/guardrails.md): a deployment setting a handler reads is a constant of the part that reads it, written by that part's slice, a requirement the seed and the host satisfy — the component answers HTTP and deliveries, the routers reach every handler, the settings come from the host — is yours to cover, since the seed was scaffolded before any slice, and credential validation or rotation, client construction, table prefetch, a flag that decided whether the consumer or listener ran, signals, periodic jobs, and lifecycle types write nothing and are left out of `covered`.
- **Reuse within your stem; do not write another stem.** Where your slice `depends-on` an earlier slice of **your own stem** (`crates/<stem>/src/<earlier_part>.rs`), import and call `crate::<earlier_part>::*` for the types, XML or JSON deserialization, validation, and conversion the earlier slice built — never duplicate its parser, types, or conversion in your own module. If integrating your slice exposes a defect in `crates/<stem>/src/<earlier_part>.rs` (such as an outer XML root wrapper struct, missing wire fields, or a filter mismatch), fix `crates/<stem>/src/<earlier_part>.rs` through `edit_files` while keeping every test in `crates/<stem>/tests/` passing. A test of yours that compensates for the earlier part — a `now` shifted by the event's own seconds so the delay comes out right, a field the wire never carries supplied so the parser accepts the message — has found that defect: repair the part, and let the test state the wire as the fixture spells it. Where your slice depends on **another stem**, depend on its crate as `<other>.workspace = true` if the tree holds it, or implement against the design's types in your own module if it is not in the tree yet; never write a crate or module for a stem your requirements do not lead with.

A requirement, a scenario, or a design type that names the source's platform — a broker and its consumer, a vault, an agent, a timer, a server — is read for the behaviour behind it and lands as the [translation](references/translation.md) says: the capability that plays the role, the mechanism's own parts written nowhere, and a requirement whose whole statement is the mechanism left out of `covered` rather than stubbed, its marker left standing. The signatures of the route functions, the messaging router, the two folds of `common`, the capability traits, and the test doubles, as the pinned crates spell them, are in [the omnia API](references/omnia-api.md): read them there rather than probing the crates through the shell. What a guest cannot do, what the host does for it and is never simulated, and the capability it reaches instead, is in the [guardrails](references/guardrails.md).

Read your scaffolded files, `crates/`, and the topic table before writing: a slice built before this one, or a resumed build, may already hold a part, a constant, or a type you use, and a file the brief names as held was written by an earlier slice or run and holds whatever stands in it.

## The loop

Once your edits are in, mark the time (`touch "$TMPDIR/before"`), then run each check in `$WORKSPACE` and read what it prints, in this order (when your slice is `start` and the adapter scaffolded no stem crate under `crates/`, skip steps 1 and 2 and start at step 3):

1. `cargo clippy -p <stem> --all-targets -- -D warnings` — your crate and its tests, under the workspace's lints: `pedantic` and `nursery` among them, every `pub` item documented, no `unsafe`, and the host boundary, which the [guardrails](references/guardrails.md) spell: a `disallowed` method, type, or macro names the capability to reach instead, and the repair is that capability, since the lints are forbidden and no `allow` or `expect` lifts one. A handler `routes()` does not name, or a part the entry does not list, is dead code here. The first run resolves the workspace, which writes `Cargo.lock`, which stays, and `target/`, which `.gitignore` keeps out of the tree. A failure in a crate not yours is a type the design names and your module misuses, or a crate that is not there yet, which you work around in yours.
2. `cargo test -p <stem>` — your crate's tests; they fail only for what your module does not yet do, and a test still ignored is one you have not filled.
3. `cargo check --target wasm32-wasip2` — every crate for the guest, so your lines resolve and your module compiles for the target; a crate that reaches past the component fails here, and the module that named it is the one to change.
4. `cargo +nightly fmt --all -- --check`, where `rustup run nightly rustfmt --version` succeeds; otherwise skip it — the formatter's configuration takes nightly `rustfmt`. A file it names is one you reformat through `edit_files`, or `write_files` whole, as it reports; the formatter may wrap a list statement over several lines, which is still one entry.
5. `find . -type f -not -path './target/*' -newer "$TMPDIR/before"` — once the checks pass, this names the files you edited and `Cargo.lock` alone. Any other path is something a check or a test left in the tree, and the whole change set of this copy is what gets sealed as your slice's commit: remove each such path through `delete` before you report.

Fix what a check reports, through `edit_files` within a file or `write_files` for a file whole, and run it again until the checks pass. Report only once they pass and the last names nothing but yours, or once a check fails for a reason outside your slice, which the report then leaves uncovered.

## Report

Answer with one JSON object:

- `covered` — each requirement id the specification above holds that your module now implements and its test confirms, once each, including a requirement whose scenario `THEN` was rendered as `[unknown]` when your test asserts the outcome stated by the requirement's statement itself. Leave an id out rather than claim what the tree does not hold or a test does not pass.
- `written` — the files the two tools wrote, once each, as a `/`-separated path relative to `$WORKSPACE`: the scaffolded files you edited, and the lists you added a line to. A file the adapter scaffolded and you did not touch, a seed file, and `Cargo.lock` are the tree's whether or not you list them.

The report is held to the tree before it is accepted. Check your tree against this list before you report, since each rule it breaks comes back as a finding under `## Findings` with every line named, and a report that breaks none is accepted first time:

- No marker of a covered requirement stands: a `todo!("REQ-..")` naming an id in `covered`, in a handler's or a function's body, is a finding at its line, filled through `edit_files` or the id left out of `covered`.
- Every scenario of a covered requirement is its test, filled and run: a scaffolded test still under `#[ignore = ..]`, or still holding its `todo!`, or missing from the file, is a finding naming the test and the scenario, filled through `edit_files` with its `#[ignore = ..]` line removed, or the id left out of `covered`.
- The root `Cargo.toml` stands as the seed spells it outside its two stem lists; a finding gives the `-` lines to put back and the `+` lines to drop.
- No crate is written beyond the stems the adapter scaffolded for this slice: `crates/order/` for `order-items`, or a crate for a stem your requirements do not lead with, is a finding naming the directory, whose files are removed through `delete` and whose lines are dropped from the root `Cargo.toml`.
- No module under `crates/*/src` is the process: a function that starts, stops, runs, listens, serves, bootstraps, or shuts down, or a `Main`, `App`, `Server`, or `Application` type, is a finding at its line, and the module is removed with its `pub mod` line and its test rather than renamed.
- Every crate a stem's `[dependencies]` names beyond the layout's six fixed lines is spelled by a module or a test of the stem, as `uuid::Uuid` spells `uuid` and `quick_xml::de` spells `quick-xml`; one no file spells is a finding at its line, repaired by using the crate where the slice meant to or removing its line through `edit_files`.
- Every constant of `crates/common/src/topic.rs` is named by a module, as `topic::<NAME>` through `config::topic` or `config::topic_for`; a constant nothing publishes or consumes is a finding at its line, named from the part that publishes or consumes it or removed with its doc comment.
- No read of the store under a constant key — `StateStore::get(provider, KEY)` — answers its miss as nothing anywhere in the function that reads: a `return Ok(Vec::new())`, an `.unwrap_or_default()`, an arm naming `None` whose body is an empty collection — `None => HashMap::new()`, `Ok(None) | Err(_) => Ok(HashMap::new())` — or an `Ok(Vec::new())` standing as the function's tail once the hit has returned above it, is a finding at the answering line, while a default on the hit's own arm — `Some(bytes) => decode(&bytes).unwrap_or_default()` — decodes what the store held and is none; on `Ok(None)` the function fetches the table from its upstream, stores it under the same key with a TTL, and answers what it fetched. A read under a key built from the input is a lookup and passes.
- No `Deserialize` struct under `crates/*/src` wraps an HTTP response in a single `data` field (`struct ... { data: ... }`): `data` is the source's HTTP client property (`response.data`) and never a JSON field on the wire, so the wrapper struct is a finding at its line, removed through `edit_files` to deserialize `response.body()` directly into `Vec<T>` for a JSON array or a struct with the body's fields at its root.
- Every stem that publishes is reached: a part spelling `Publish` in a stem whose entry registers no part's `routes()` or `topics`, and whose crate no other stem's module names, is a finding at the part's line, since the host runs a stem through its two folds alone; the repair is the trigger the design's inbound stream bullet spells — the constant at the end of the topic table, the `.route(..)` with `messaging::consume_with(<handler>, <decode>)` in the part's `topics(..)`, and the part's entry at the end of the stem's array — never a requirement invented for it.
- No refusal is answered `Ok(())`: a `return Ok(())` or a tail `Ok(())` inside a `let Ok(..) = .. else` block, an `Err(..) =>` arm, an `if ..is_err()` branch, or a `let Some(..) = ...ok() else` block answers a delivery or a call the code refused as processed, and is a finding at its line; the repair returns the error with `?` — `bad_request!` for a validation or timeliness rejection, `bad_gateway!` for an upstream that refused — and `Ok(())` is answered only for a valid message a rule filters out.
- No setting names a format: a `const NAME: &str = "NAME"` whose name spells `FORMAT` (`DATE_FORMAT`) reads a parser's syntax from the deployment, and is a finding at its line; a format a criterion spells (`DD/MM/YYYY`) is a `const` of the module that parses with it, holding the parser's own syntax (`"%d/%m/%Y"`).

Repair a finding through `edit_files` where it is a change within a file, `delete` where a module goes, then answer again; the report is yours once the tree stands.

## Worked example

A slice `orders-reading` (`SLICE-006`) implementing `REQ-030` and `REQ-031`, the first part of the `orders` stem, which another slice also builds this wave. The adapter scaffolded the stem's manifest and entry, the part with a handler per route and an ignored test per scenario, and the stem's lines in the root lists; the turn filled the handlers and the tests, added a `chrono` line to the stem's manifest for the order's timestamp, and declared the constant of the topic it publishes to in the topic table. `REQ-031` depends on a `customers` module another slice is building this wave, so its test cannot pass yet: its marker and its ignored test stand as scaffolded, and it is left uncovered:

```json
{
  "covered": ["REQ-030"],
  "written": [
    "crates/orders/Cargo.toml",
    "crates/orders/src/reading.rs",
    "crates/orders/tests/reading.rs",
    "crates/common/src/topic.rs"
  ]
}
```

## Worked example: a `start` slice

The slice `start` (`SLICE-001`) holds nine requirements read from the process the source was: `REQ-001` and `REQ-002` state the vault secret and rotation watcher it started with, `REQ-003` the token it exchanged at start and refreshed hourly, `REQ-004` the brokers it connected to, `REQ-005` the consumer group it joined, `REQ-006` the APM agent it initialised, `REQ-007` the signal handler that drained it, `REQ-008` the `Main` class that ran it all, and `REQ-009` the job it scheduled to reload a table every ten minutes. By the table in [what `start` becomes](references/guardrails.md) the seed and the host are `start`: the adapter scaffolded nothing for the slice, and it writes no module for the vault, the token, the brokers, the agent, the signals, the `Main`, or the job, and no key in the state store recording that any of them ran. Its report covers `REQ-004`, since the host and the seed's topic list answer deliveries as stated, writes nothing, since the seed was scaffolded when the repository was initialised, and leaves the other eight out:

```json
{
  "covered": ["REQ-004"],
  "written": []
}
```
