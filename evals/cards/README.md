# Eval cards

Scorecards the eval runner (`cargo run -p evals`, [evals/README.md](../README.md)) wrote under `target/eval/`, copied here by hand because `target/` is gitignored and `make sweep` drops what sits there untouched for a week. Each is one dated run of the eval over the cases named in its headings, and each records the model, the number of runs a case, and — per run — the exit code, the wall time, the completions the run opened with their tokens, the requirement and criterion recall against the case's `expected.toml`, the stems, and the misses by anchor. The runner keeps writing to `target/eval/`; a card worth keeping is copied in, never edited.

A card stays in the tree while a decision this README records rests on it, and leaves when a later decision supersedes that one. What the tree holds now is the four graded arms of the second experiment (`21-33-27Z`, `22-28-34Z`, `23-30-54Z`, `00-57-10Z`), the evidence the standing verdict rests on and the baseline the next card is read against — noting that the four fixes recorded under **Adopted** landed after them, so the first card after those is the new baseline. The ten cards before them — the survey-by-model baseline, the parser's checks, and the first experiment's three arms — graded a detection half of `surface.rs` this tree no longer ships; their findings stand in the tables below, and each card is read from history as `git show 2e362e1:examples/eval/cards/<card>.md`. The `python` adapter's cards are the two sections after it, predictions and decision rules written before any run: the first arms' two baselines (`10-46-48Z`, whose findings the three rules recorded there rest on, and `12-05-47Z`, the six authored cases' baseline), and the loop round's — the two real cases' first card and its rerun (`21-42-36Z`, `22-30-32Z`), Arm 3's card over the eight cases with the anchor-reading run beside it (`22-58-28Z`, `00-03-35Z`), Arm 2's off arm (`00-16-57Z`), and the second model's card (`00-35-07Z`).

The `emery` and component (`typescript.wasm`, `python.wasm`) paths a card's header cites are the build the run used — a Cursor sandbox cache of this tree's `cargo-target`, not a path this repository holds — and say nothing beyond which binary answered.

## Adopted

The default is what this tree ships: the model names the surfaces and code derives the rest, the detection half of `surface.rs` and the `model-survey` feature gone, one survey turn scripted per workspace scenario in `tests/source.rs` ([RELEASES.md](../../RELEASES.md) has the entries). The four loose ends the second experiment left (its verdict is the last section below) are closed on the same branch. An exported class's surface carries its public methods as ids, read at the anchor as the parser's `exports()` had read them (`typescript_exports`, `typescript_survey_methods`). The `nestjs-boilerplate` expectation reads the two `run-seed.ts` as `run-seed` commands, the prompt's reading, so the `+2` those six runs graded is expected. Two surfaces alike at their anchors are told apart by the nearest segment of their entries' paths that spells neither the stem nor the id's own tail — `files.upload.local`, `files.upload.s3` (`typescript_survey_alike`). And a stem the code spells at an anchor — a route's resource under its mount or prefix, a literal's first word — replaces the survey's, the model's standing only where the code spells none (`typescript_survey_stem_derived`, `typescript_callbacks`), so the one drift in twenty-eight triples (`worker` for `invoices`) cannot recur for a registration led by a literal. The two things the checkpoint settled stand as settled: the coverage gate asks after the modules the facts locate a surface in and no others, and the ladder's longer rungs stay in the runner for a case that reaches them.

## The survey-by-model experiment

Two arms of the `typescript` adapter over five cases — the four above and `api-routes`, a Next.js app-router API the parser has no rule for — three runs each under `composer-2.5`, the treatment once more under `gpt-5.3-codex`. The control is the parser's survey as shipped. The treatment is the `model-survey` feature: the parser reads the tree as before, then one `survey` turn hands the model what it read — the manifest, the bootstrap, every call that hands a function to a package's receiver, every decorated method, what the entry modules export, the packages imported, the modules laid whole — and the model names each surface, anchors it where the code registers or declares it, and gives it the stem its ids lead with under the convention `survey.md` states; code derives the closure each anchor reaches, the bootstrap's `start`, the ids, the anchors, and the briefs exactly as it does from its own surfaces, so the seams differ in the naming alone. The eval grades what it always graded and, new for this experiment, the `(entry, stem)` pairs the survey decided against each case's `[[surface]]` table, the stem sets across runs, and the pairs every two runs share; a run the backend's cap ends re-runs one rung up `EVAL_LADDER` and the card's `Budget ladder` says where it landed, while the comparison columns stay at the defaults.

The predictions below were written before the arms were built, and the rows after them record what the cards showed against each.

### Predictions

- **Control, `composer-2.5` × 3.** The four existing cases: stems `exact` on every run, recall at the `12-54-15Z` floor — `cli-jobs` 17/17, `express-orders` ≥ 29/30, `orders` 6/6, `r9k` ≥ 28/32 — and surfaces exact, since the parser decides them the same way on every run. `api-routes`: the parser finds no bootstrap (no `main`, no conventional entry that runs anything) and no registration, so `exported()` falls to the modules nothing imports — the four route modules — and names their exported handlers as surfaces under the stems their names give: `get`, `post`, `delete`. The card reads stems `-3 +3`, surfaces `0/4 +3` or thereabouts, and every requirement matched by anchor lands `0 in stem`. That measures a convention the parser has not been taught — a file-path rule of some twenty lines — not a permanent inability, and is stated as such.
- **Treatment, `composer-2.5` × 3.** One `survey` completion more per run, 20–60 s and 10–40 K input tokens. Stem sets identical across the three runs on `cli-jobs`, `express-orders`, `orders`, and `api-routes`; `r9k` the likeliest to drift, because `kafka-consumer` comes from the receiver's type and a model may prefer `consumer` or `messages` despite the convention. The `cli-jobs` risk is `invoice-worker` for the worker on the queue `invoices`, and `nightly-job` for the cron schedule. Surfaces exact on `express-orders` and `orders`; `cli-jobs` may lose the `nightly` command's pair to the schedule's. Recall within one requirement of the control on each of the four parser-covered cases. `api-routes` surfaced per resource — `orders`, `customers`, `health` — with stems exact and recall ≥ 13/16.
- **Treatment, `gpt-5.3-codex` × 3.** Stem agreement the same or better than under `composer-2.5`; the `03-56-54Z` card showed the reasoning model differs enough to matter, and its recall spread is the wider.
- **Budget.** No run on either arm hits a cap at 600/120 under `composer-2.5`; the codex survey turn stays under 200 s. A case that does hit a cap passes at 1200/240.

### Decision rule

- **Treatment wins**: stem sets identical across all three runs on at least four of the five cases, exact against the expected stems on the four parser-covered cases, recall within one requirement of the control, and `api-routes` surfaced per resource. The consequence, for a later branch: the model names and the parser derives; `surface.rs` shrinks to `start()`, `identify()`, and the closure glue, with one scripted `survey` turn per `typescript` scenario in `tests/source.rs` as the price.
- **Control wins**: stem sets differ across runs on two or more cases despite the stated convention — naming needs code.
- **Either way, the likely landing**: the model survey replaces the parser's `unsurfaced` / by-directory fallback, used only where the parser finds no surface. `api-routes` decides that on its own.

## The survey-default experiment

The question the first experiment left open: could the model survey be the survey — the model naming and the parser deriving, the detection half of `surface.rs` gone — rather than the fallback where the parser finds nothing? Four arms this time, the two of the first experiment and a `gpt-5.3-codex` control beside the codex treatment so the recall clause can be judged under that model too, three runs each over nine cases: the five above and four written to probe where the parser's conventions read a tree wrongly, at scale and in kind ([evals/README.md](../README.md) describes each). Three changes precede the runs, all on this branch: the model arm's surfaces now carry a discriminator code derives at the anchor — a registration's handler name or its route, a decorated member's name, an export's name with the path segments past the stem — never the model's name, which is what made the `api-routes` ids 0% stable above; the parser reads the object form `@Controller({ path })` (both arms, since without it the control fragments real NestJS code into one stem per route); and the treatment lays the modules its facts cite — the bootstrap, the modules that register or decorate — before the rest, so the scale case's budget goes to the surfaces rather than to whatever sorts first. The eval grades a surface found at its entry under another stem as restemmed (`~k`), telling a parser that is present but wrong from one that is absent, and carries the treatment's `unreached` count into the notes.

The predictions below were written before the arms were built. The control's are read from `surface.rs` and are confirmed at the checkpoint, not assumed; where the plan's draft read the parser differently, the reading here is the later, closer one and the checkpoint decides.

### Decision rule

- **Default earned** — all three: (1) the id fix holds: `api-routes` id `Stability` in band and ids unique on every treatment run; (2) the three wrong-parser cases (`hono-mounted`, `cli-table`, `fastify-demo`): treatment stems exact and surfaces ≥ 3/4 by entry on ≥ 2/3 runs each, while the control reads its predicted signature; (3) scale: treatment stem sets identical across the 3 runs, ≥ 9/10 surfaces by entry, `unreached` ≤ 10%, at some rung ≤ 2400/480, and recall within one requirement of the same-model control on the small cases and within 10% on the scale case. The consequence, for a later branch: the model names and code derives — the detection half of `surface.rs` (`survey`, `mounts`, `callbacks`, `decorated`, `exports`, the convention tables) is deleted, the feature and its `cfg` arms dropped, one survey turn scripted per workspace scenario in `tests/source.rs`.
- **Fallback stands** — the first experiment's landing: (2) passes but (3) fails at every rung or drifts across runs; the model survey stays where the parser finds no surface.
- **Rework, no verdict**: (2) fails the way the `fastify-demo` risk names — the model over-trusts the facts brief — which indicts the brief, not the idea; the brief is fixed and the arm rerun, documented here.

### Results

**The checkpoint.** Six passes of `EVAL_RUNS=1` under `composer-2.5` preceded the graded runs, none copied in; the plan allowed fixes here and nowhere after, and this records what they were, since there were more than the first experiment needed.

The control read three of its four predicted signatures on the first pass: `hono-mounted` `1/4 ~3`, `-3 +1`; `cli-table` `1/4 ~1`, `-3 +1` (the one surface `Command.option("--dry-run")` under `command` — the chain's last call rather than `.action`, the same stem); `fastify-demo` `1/9 +2`, `-8 +2` — one extra fewer than predicted, the `GET /` in `routes/api/index.ts` surfacing under nothing, since its module's default export is an anonymous plugin function the parser types no receiver through. `nestjs-boilerplate` did not: `7/10 ~3 +11`, `-0 +13` in 432 s, because on real NestJS code `@ApiTags("Users")` — a class decorator with a literal, listed before `@Controller` — was taken as the class's path prefix, and `@SerializeOptions({ groups })` on a method shadowed the verb decorator beneath it. Two parser fixes (both arms): a decorator that shapes a response or documents it (`Api*`, `SerializeOptions`, and the standing noise list) names no route and gives no prefix, and the prefix is the first class decorator that is not one of those; `typescript_decorated_object_path` in `tests/source.rs` carries both. After them the control read `9/10 ~1 +9`, `-1 +9`, 296 s — the prediction exactly.

The treatment took five passes. The first, on the wasm the predictions were written against, read `hono-mounted` `4/4` exact and `cli-table` `4/4` exact (the run then died on a `bad_gateway` from the model backend during extraction, the survey done), and exposed two defects the plan had named as the checkpoint's purpose. On `fastify-demo` the survey was `exhausted`: the coverage gate — every module in neither `surfaces`' closure nor `unreached` is a finding — demanded the autoloaded `plugins/` be reached or listed, and the model invented eleven plugin surfaces to satisfy it and still missed a route. On `nestjs-boilerplate` the survey named `apple`, `facebook`, and `google` as stems beside `auth` — the named risk — and one extract seam was `exhausted` on the `excerpt` field the first experiment's control met. Fixes: the gate's finding is raised only for a module the facts locate a registration or a decorated method in, the rest counted as unplaced by code (`placed by model … unplaced=N`, which the eval now reads as `unreached`); the prompt's unreached section names a plugin folder an autoloader walks, and the stem rule spells `POST /auth/google/login → auth` out. The second pass read `api-routes` `4/4` exact with thirty requirement ids, unique, all led by code-derived discriminators (`customers.get.*`, `orders.get-id.*`, `orders.delete-id.*`); `cli-table` `4/4` exact with the commands anchored at the table rows in `cli.ts` — better than predicted; `hono-mounted` `4/4` exact; `nestjs-boilerplate` `10/10` exact in 322 s with 18 unplaced (11% of 159: the seed and migration tree, the two lint configs, two modules nothing imports); and `fastify-demo` `5/9 +1`, `-4 +1` — the four `scripts/*.ts` neither named nor listed, the root route named `index`, and three `tasks` routes sharing the id `tasks.post.tasks`, since `route_discriminator` took `assign` in `/:id/assign` for the resource when the module's mount is one `autoload` adds and code cannot read. ### Arm 3 — decorator anchors

The rule under test: a decorated `def` is listed in the facts, and accepted as a surface, at its whole span — `app/routers/orders.py#L40-L49`, the decorator through the last line of the body — so every line of a handler is a surface's own line and a requirement anywhere in it passes the anchor gate.
