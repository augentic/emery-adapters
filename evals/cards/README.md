# Eval cards

The record of the scorecards the eval runner (`cargo run -p evals`, [evals/README.md](../README.md)) wrote under `target/eval/`. A card is one dated run of the eval over the cases named in its headings, recording the model, the number of runs a case, and — per run — the exit code, the wall time, the completions the run opened with their tokens, the requirement and criterion recall against the case's `expected.toml`, the stems, and the misses by anchor. `target/` is gitignored and `make sweep` drops what sits there untouched for a week, so no card is in the tree: a card a decision rested on was committed beside this file, never edited, until its decision was written, and is read from history at the commit [the index](#rounds) names; a later card's figures were read into its round as they stood under `target/eval/`, and the round is its record. What stays is this directory — this README for the protocol, the rules adopted, and the index, and one file per programme of rounds, each round's predictions, its rule, and each card's figures read against them.

The `emery` and component (`typescript.wasm`, `python.wasm`) paths a card's header cites are the build the run used — a Cursor sandbox cache of this tree's `cargo-target`, not a path this repository holds — and say nothing beyond which binary answered.

## Protocol

Every round follows one protocol, and the rounds that ran it are where its rules were learned.

- **Predictions first, then the rule, then the runs.** The predictions and the decision rule are written into the round's file before an arm is built, each arm is three runs under a pinned `CURSOR_MODEL`, and the card's figures are read into it against the rule — the result column and the decision — rather than the card kept beside it. An expectation moves only where the code's own rule, checked against the anchor and stem rules, says the expectation was wrong, and the move is recorded with the card.
- **A rule is written on the near-deterministic columns.** Surfaces by entry, stems, the refused claims and corrected seams, the correction rounds of the survey turn, and the rung a run landed on are decided by code or by the model's one reading of a convention, and they held or moved exactly on every arm so far. Recall is the model's naming of behaviours run to run: one component's own spread over six runs on `fastapi-template` was 29–35 of 36, wider than any arm's effect in the loop round, so three runs cannot tell a one-requirement difference from noise and a rule never turns on recall alone — it is read as a band, and a clause on it says "within the band", never "greater than".
- **"No run fails" reads "before grading".** A run the backend refuses before any claim is accepted is the host's failure, and the runner puts it again once. A run that fails after its claims are accepted — in the engine's own turns — is graded on them and the engine's failure is recorded against the engine, not the arm; the card names the turn it died in.
- **An off arm is built from a worktree.** A rule under test has no feature flag, so its off arm is a local edit to the one function named, built from a detached worktree ([evals/README.md](../README.md) has the commands), run, and never shipped; the working tree never holds the off state, which the loop round learned when an in-flight arm edit was swept into an unrelated commit.
- **A card is read back to its anchors.** The runner stages every run under `target/eval/<card>/<case>/`, so a card's `run-N.evidence-*.json` and `run-N.facts.md` outlive the next invocation and a second clause — where the matched requirements landed, which the misses-by-anchor cannot show — is read from the card's `requirement anchors` line rather than from three more runs.
- **A target card is a `--rebuild`.** The first build card over a case is `--build`, which commits a revision and builds it; every target card after it is `--rebuild <that card> --target <name>`, which copies the card's staged project, drops the repository its build labelled, and builds the same committed revision again under this invocation's binary, component, model, and width, so one plan is built under each target and the plan's own variance is out of the comparison. The omnia target's first card rebuilt the boundary card's `express-orders` plan, and what differed from that card's row was the target and the toolchain under the fence and nothing of the plan, the boundary, the backend, or the model. A change to type mapping or prompt constraints is checked against a reference-oracle case (`--oracle <card> train`) rather than the turn's self-authored tests alone.
- **An omnia card is a pair.** Every omnia build card is one command run twice over one component: under `emery` and `composer-2.5`, the large-model arm, and under `emery-dev` and `openai::Qwen/Qwen3-Coder-Next-FP8`, served by vLLM on a RunPod H200 and reached through an SSH tunnel, the small-model arm, with the recipe and knobs [evals/README.md](../README.md#the-small-model-arm) states (`OPENAI_API_KEY=local`, `GENAI_ENDPOINT=http://127.0.0.1:11435/v1/` over the tunnel, `EVAL_JOBS=1`, `EVAL_BUILD_RUNG=7200/600`, `GENAI_MAX_ROUNDS=64`, `GENAI_MAX_CANDIDATES=3`, `GENAI_MAX_REPEATS=5`, the server's context length set to `262144` under `--tool-strict-level function`, the backend's other caps at their defaults unless the round names them); the local `qwen3-coder:30b` under Ollama is the fallback where no pod is up, and a card says which model it ran. Whoever runs the round runs both — the agent asked to run an omnia eval included, bringing the server up where none answers and closing the tunnel or stopping the local server after — the small-model arm after the large-model one, since one run holds the server. Where a round changes what one slice's turn reads rather than the plan, the small-model arm is run as probes: one `--resume <large-model card> --at <wave>` per wave of the large-model arm's chain, each over the tree the large model built up to that wave (Round H: `--resume 2026-10-21T06-28-53Z --at k` for k = 2..6, one at a time), so every slice is measured over a tree the small model did not have to build first, and a probe that builds on yields whole-build evidence besides; a control under the earlier round's artifacts on the same command runs first, so what the server or the knobs alone move is read before the round's items are, and the round's predictions are written per slice against that control. The round's predictions name both arms before either is built: the large-model clauses are read against the `composer-2.5` band and the small-model clauses against the band of the model it ran (under `Qwen3-Coder-Next`, `2026-10-21T05-21-29Z` and `2026-10-21T07-04-07Z` until a card passes them; under the 30b, C1, `2026-10-19T22-47-32Z`), and a difference between the two arms is the model's alone, since the plan, the component, and the knobs are one. A round whose small-model arm could not be put — no pod and no server, the model not pulled, the tunnel down, the machine held by another run — records why in its results and is not decided until it has run; the small-model run is never left for later by omission, and the register and the scaffold are what a small model reads, so a change to either is checked under it before it ships.
- **The small-model arm is a ladder, and `k = 2` is the gate.** Decided on 2026-10-22, after Round H: the small-model arm is a goal, pushed through the untrained levers before any model is trained. The levers are rungs in cost order — rung 0 the harness debt Round H exposed (each item lost a probe or misled the model); rung 1 the sampling (temperature 0 at the server, 0.2 where 0 loops); rung 2 the model (a dense ~32B coder in FP8 under the same recipe, then the largest open coder one H200 serves); rung 3 the edit addressing (a tool that fills a marker by its id or inserts at a named anchor, no copied span); rung 4 fewer markers (`z.infer` aliases and static tables laid, the route function's pre-rendering broadened) — one rung a round, Round I rungs 0 and 1, Round J rung 2, Round K rung 3, Round L rung 4. Every rung is read at `k = 2`: one or two `--resume 2026-10-21T06-28-53Z --at 2` probes over the same tree, plan, and brief as `2026-10-21T21-00-02Z`, so the rung's `health` turn reads against that card's — 64 rounds, 6.4 edits a marker, 12 `find`s refused, 5 whole writes refused, the report refused by `manifest_drift` — about a quarter of an hour of pod time and a dollar, where Round H's six later puts cost 1 h 45 and $9 to confirm what its two `k = 2` probes had said. A probe that builds `health` to its label is followed by `k = 3..6` and a `--rebuild`, the full ladder; one that does not is read for which failure mode remains (the copying: `find`s refused, edits a marker, `omnia` misspelled; the finishing: rounds to the cap) and the next rung runs. Training starts when the best untrained configuration still fails `k = 2`, or when `k = 2` builds and what remains at `k ≥ 3` is what the checks catch and no harness repairs — coverage claimed over ignored tests, a store stubbed under a comment, a module or a crate imagined. Off the table: raising the round cap, splitting slices or lowering `SLICE_CAP` (12), one marker a turn, an arm as a Cargo feature. The runner puts the seed's verify once under a resume, whatever the wave — the earlier build's empty slices before the wave sealed over the moved label but the first — so a probe at `k ≥ 3` pays one verify's odds before its slice, not two.
- **A denial reading is `file-*` and `network-*` alone.** The kernel boundary's refusals are read from macOS's unified log over the run's window (`log show --start … --end … --predicate 'eventMessage CONTAINS "deny"' --style compact`), filtered to the bridges' and their tools' pids, and read for the `file-read-*`, `file-write-*`, and `network-outbound` kinds, each by its path or host: a toolchain under `$HOME` the target's worker grant does not name is a root for the adapter's `grants` to spell, a tool's walk up from the lend is the fence doing its work, a system path is the profile's and a finding. The `sysctl-read`, `mach-lookup`, and `system-info vfs.disk-space` kinds are the profile's own noise, every bridge's and every tool's — 99 in 100 of the omnia target's first card's 150,000 lines — recorded once, under the boundary card, as the baseline a new kind is told from, and never a widening to ask for.

## Adopted

The default is what this tree ships: the model names the surfaces and code derives the rest, the detection half of `surface.rs` and the `model-survey` feature gone, one survey turn scripted per workspace scenario in `tests/source.rs` ([RELEASES.md](../../RELEASES.md) has the entries). The four loose ends the second experiment left ([the survey-default experiment](typescript-survey.md#the-survey-default-experiment)) are closed on the same branch. An exported class's surface carries its public methods as ids, read at the anchor as the parser's `exports()` had read them (`typescript_exports`, `typescript_survey_methods`). The `nestjs-boilerplate` expectation reads the two `run-seed.ts` as `run-seed` commands, the prompt's reading, so the `+2` those six runs graded is expected. Two surfaces alike at their anchors are told apart by the nearest segment of their entries' paths that spells neither the stem nor the id's own tail — `files.upload.local`, `files.upload.s3` (`typescript_survey_alike`). And a stem the code spells at an anchor — a route's resource under its mount or prefix, a literal's first word — replaces the survey's, the model's standing only where the code spells none (`typescript_survey_stem_derived`, `typescript_callbacks`), so the one drift in twenty-eight triples (`worker` for `invoices`) cannot recur for a registration led by a literal. The two things the checkpoint settled stand as settled: the coverage gate asks after the modules the facts locate a surface in and no others, and the ladder's longer rungs stay in the runner for a case that reaches them.

Before the two `typescript` experiments, seven cards (`2026-09-28T21-21-56Z` through `2026-09-29T12-54-15Z`, read as `git show 2e362e1:examples/eval/cards/<card>.md`) graded the parser's own survey as each rule was taught it, over `cli-jobs`, `express-orders`, `orders`, and `r9k`, a case since retired. Three readings of theirs stand: the function heads joined the anchor set when `05-06-47Z` exhausted a run on four requirements refused at method declarations; the `queues.ts#L16-L25` expectation moved to `start`, since a construction with a boundary's value is `start`'s by the prompt's rule and every run followed it; and run-to-run id `Stability` read 10–31% throughout, so it measures the model's naming of each id's second segment and is no target the survey holds.
