# Eval cards

The record of the scorecards the eval runner (`cargo run -p evals`, [evals/README.md](../README.md)) wrote under `target/eval/`. A card is one dated run of the eval over the cases named in its headings, recording the model, the number of runs a case, and — per run — the exit code, the wall time, the completions the run opened with their tokens, the requirement and criterion recall against the case's `expected.toml`, the stems, and the misses by anchor. `target/` is gitignored and `make sweep` drops what sits there untouched for a week, so a card a decision rested on was committed beside this file, never edited, until its decision was written; what stays is this README — each experiment's predictions, its rule, and each card's figures read against them — and the cards are read from history.

No card is in the tree. Twenty are read as `git show 098dd54:evals/cards/<card>.md`, a `main` commit holding every one: the four graded arms of the second experiment (`21-33-27Z`, `22-28-34Z`, `23-30-54Z`, `00-57-10Z`), the evidence the standing verdict rests on — noting that the four fixes recorded under **Adopted** landed after them; the `python` adapter's, in the two sections after it, predictions and decision rules written before any run — the first arms' two baselines (`10-46-48Z`, whose findings the three rules recorded there rest on, and `12-05-47Z`, the six authored cases' baseline), and the loop round's: the two real cases' first card and its rerun (`21-42-36Z`, `22-30-32Z`), Arm 3's card over the eight cases with the anchor-reading run beside it (`22-58-28Z`, `00-03-35Z`), Arm 2's off arm (`00-16-57Z`), the second model's card (`00-35-07Z`), and the check of the one fix it asked for (`02-37-57Z`); the shared rules' two (`20-40-46Z`, `21-54-26Z`); and the documentation survey experiment's five — the control over the eleven cases (`00-07-32Z`, the baseline every later documentation card is read against), the two treatment arms over the six documentation cases (`01-40-22Z`, `02-15-00Z`), and the synthesis arm over the five cross-source cases under two models (`02-53-51Z`, `03-28-41Z`). The ten cards before them — the survey-by-model baseline, the parser's checks, and the first experiment's three arms — graded a detection half of `surface.rs` this tree no longer ships, and are read as `git show 2e362e1:examples/eval/cards/<card>.md`. The documentation round's second three — the grain arm over four documentation cases (`06-51-01Z`, read against E1), the brief case under the control (`06-53-25Z`), and the engine arm over the three cross-source cases (`07-05-39Z`, read against E3) — were committed only on the branch that removed them (`0254e5b`), never on `main`, and the last section's table and grader's note are their record. The build arm's card (`2026-10-09T04-17-59Z`, the first card with the five build columns) and the smoke before it (`04-13-39Z`) stand under `target/eval/` with the builds' own files beside them, their decisions written in [the build arm](#the-build-arm), which is their record; the write-path arm after it is written ahead of its run.

The `emery` and component (`typescript.wasm`, `python.wasm`) paths a card's header cites are the build the run used — a Cursor sandbox cache of this tree's `cargo-target`, not a path this repository holds — and say nothing beyond which binary answered.

## Protocol

Every experiment below follows one protocol, and the rounds that ran it are where its rules were learned.

- **Predictions first, then the rule, then the runs.** The predictions and the decision rule are written into this file before an arm is built, each arm is three runs under a pinned `CURSOR_MODEL`, and the card's figures are read into this file against the rule — the result column and the decision — rather than the card kept beside it. An expectation moves only where the code's own rule, checked against the anchor and stem rules, says the expectation was wrong, and the move is recorded with the card.
- **A rule is written on the near-deterministic columns.** Surfaces by entry, stems, the refused claims and corrected seams, the correction rounds of the survey turn, and the rung a run landed on are decided by code or by the model's one reading of a convention, and they held or moved exactly on every arm so far. Recall is the model's naming of behaviours run to run: one component's own spread over six runs on `fastapi-template` was 29–35 of 36, wider than any arm's effect in the loop round, so three runs cannot tell a one-requirement difference from noise and a rule never turns on recall alone — it is read as a band, and a clause on it says "within the band", never "greater than".
- **"No run fails" reads "before grading".** A run the backend refuses before any claim is accepted is the host's failure, and the runner puts it again once. A run that fails after its claims are accepted — in the engine's own turns — is graded on them and the engine's failure is recorded against the engine, not the arm; the card names the turn it died in.
- **An off arm is built from a worktree.** A rule under test has no feature flag, so its off arm is a local edit to the one function named, built from a detached worktree ([evals/README.md](../README.md) has the commands), run, and never shipped; the working tree never holds the off state, which the loop round learned when an in-flight arm edit was swept into an unrelated commit.
- **A card is read back to its anchors.** The runner stages every run under `target/eval/<card>/<case>/`, so a card's `run-N.evidence-*.json` and `run-N.facts.md` outlive the next invocation and a second clause — where the matched requirements landed, which the misses-by-anchor cannot show — is read from the card's `requirement anchors` line rather than from three more runs.

## Adopted

The default is what this tree ships: the model names the surfaces and code derives the rest, the detection half of `surface.rs` and the `model-survey` feature gone, one survey turn scripted per workspace scenario in `tests/source.rs` ([RELEASES.md](../../RELEASES.md) has the entries). The four loose ends the second experiment left (its verdict is the last section below) are closed on the same branch. An exported class's surface carries its public methods as ids, read at the anchor as the parser's `exports()` had read them (`typescript_exports`, `typescript_survey_methods`). The `nestjs-boilerplate` expectation reads the two `run-seed.ts` as `run-seed` commands, the prompt's reading, so the `+2` those six runs graded is expected. Two surfaces alike at their anchors are told apart by the nearest segment of their entries' paths that spells neither the stem nor the id's own tail — `files.upload.local`, `files.upload.s3` (`typescript_survey_alike`). And a stem the code spells at an anchor — a route's resource under its mount or prefix, a literal's first word — replaces the survey's, the model's standing only where the code spells none (`typescript_survey_stem_derived`, `typescript_callbacks`), so the one drift in twenty-eight triples (`worker` for `invoices`) cannot recur for a registration led by a literal. The two things the checkpoint settled stand as settled: the coverage gate asks after the modules the facts locate a surface in and no others, and the ladder's longer rungs stay in the runner for a case that reaches them.

## The survey-by-model experiment

Two arms of the `typescript` adapter over five cases — the four above and `api-routes`, a Next.js app-router API the parser has no rule for — three runs each under `composer-2.5`, the treatment once more under `gpt-5.3-codex`. The control is the parser's survey as shipped. The treatment is the `model-survey` feature: the parser reads the tree as before, then one `survey` turn hands the model what it read — the manifest, the bootstrap, every call that hands a function to a package's receiver, every decorated method, what the entry modules export, the packages imported, the modules laid whole — and the model names each surface, anchors it where the code registers or declares it, and gives it the stem its ids lead with under the convention `survey.md` states; code derives the closure each anchor reaches, the bootstrap's `start`, the ids, the anchors, and the briefs exactly as it does from its own surfaces, so the seams differ in the naming alone. The eval grades what it always graded and, new for this experiment, the `(entry, stem)` pairs the survey decided against each case's `[[surface]]` table, the stem sets across runs, and the pairs every two runs share; a run the backend's cap ends re-runs one rung up `EVAL_LADDER` and the card's `Budget ladder` says where it landed, while the comparison columns stay at the defaults.

The predictions below were written before the arms were built, and the rows after them record what the cards showed against each.

### Predictions

That measures a convention the parser has not been taught — a file-path rule of some twenty lines — not a permanent inability, and is stated as such.
- **Treatment, `composer-2.5` × 3.** One `survey` completion more per run, 20–60 s and 10–40 K input tokens. - **Treatment, `gpt-5.3-codex` × 3.** Stem agreement the same or better than under `composer-2.5`; the `03-56-54Z` card showed the reasoning model differs enough to matter, and its recall spread is the wider.

### Decision rule

- **Treatment wins**: stem sets identical across all three runs on at least four of the five cases, exact against the expected stems on the four parser-covered cases, recall within one requirement of the control, and `api-routes` surfaced per resource. - **Control wins**: stem sets differ across runs on two or more cases despite the stated convention — naming needs code.
- **Either way, the likely landing**: the model survey replaces the parser's `unsurfaced` / by-directory fallback, used only where the parser finds no surface. `api-routes` decides that on its own.

## The survey-default experiment

The question the first experiment left open: could the model survey be the survey — the model naming and the parser deriving, the detection half of `surface.rs` gone — rather than the fallback where the parser finds nothing? Four arms this time, the two of the first experiment and a `gpt-5.3-codex` control beside the codex treatment so the recall clause can be judged under that model too, three runs each over nine cases: the five above and four written to probe where the parser's conventions read a tree wrongly, at scale and in kind ([evals/README.md](../README.md) describes each). Three changes precede the runs, all on this branch: the model arm's surfaces now carry a discriminator code derives at the anchor — a registration's handler name or its route, a decorated member's name, an export's name with the path segments past the stem — never the model's name, which is what made the `api-routes` ids 0% stable above; the parser reads the object form `@Controller({ path })` (both arms, since without it the control fragments real NestJS code into one stem per route); and the treatment lays the modules its facts cite — the bootstrap, the modules that register or decorate — before the rest, so the scale case's budget goes to the surfaces rather than to whatever sorts first. The eval grades a surface found at its entry under another stem as restemmed (`~k`), telling a parser that is present but wrong from one that is absent, and carries the treatment's `unreached` count into the notes.

The predictions below were written before the arms were built. The control's are read from `surface.rs` and are confirmed at the checkpoint, not assumed; where the plan's draft read the parser differently, the reading here is the later, closer one and the checkpoint decides.

### Decision rule

- **Default earned** — all three: (1) the id fix holds: `api-routes` id `Stability` in band and ids unique on every treatment run; (2) the three wrong-parser cases (`hono-mounted`, `cli-table`, `fastify-demo`): treatment stems exact and surfaces ≥ 3/4 by entry on ≥ 2/3 runs each, while the control reads its predicted signature; (3) scale: treatment stem sets identical across the 3 runs, ≥ 9/10 surfaces by entry, `unreached` ≤ 10%, at some rung ≤ 2400/480, and recall within one requirement of the same-model control on the small cases and within 10% on the scale case. The consequence, for a later branch: the model names and code derives — the detection half of `surface.rs` (`survey`, `mounts`, `callbacks`, `decorated`, `exports`, the convention tables) is deleted, the feature and its `cfg` arms dropped, one survey turn scripted per workspace scenario in `tests/source.rs`.
- **Fallback stands** — the first experiment's landing: (2) passes but (3) fails at every rung or drifts across runs; the model survey stays where the parser finds no surface.
- **Rework, no verdict**: (2) fails the way the `fastify-demo` risk names — the model over-trusts the facts brief — which indicts the brief, not the idea; the brief is fixed and the arm rerun, documented here.

### Results

### Arm 2 — the construction-at-load bootstrap

The rule under test: a module no script names and no guard runs is the bootstrap when, at load, it constructs something a package provides or calls a function of the tree that does — `wsgi.py`'s `app = create_app()` — which `Tree::bootstrap` reads through `runs_at_load` in `survey/surface.rs`. The off arm drops the construction clause from `runs_at_load`, leaving a guard, a script, or a conventional entry that calls something as the only ways a module runs. Over `flask-blueprints`, where the rule decides the bootstrap, and `fastapi-orders`, where the guard decides it and the rule must change nothing.

- **On (the baseline card).** `flask-blueprints` `4/4`, `start` present at `wsgi.py`: the factory's configuration and mounts, the timing hook, and the two error handlers — the three `start` requirements, after the first card dropped the one at the construction line itself (below) — under `start`, in stem.

Decision rule: the rule stays when the off arm loses `start` on `flask-blueprints` on ≥ 2/3 runs and `fastapi-orders` is identical across the arms; it is narrowed — to a construction through a package alone, or to a function of the tree alone — if the on arm names a module the off arm does not and the expectation reads that module as no bootstrap on any of the six cases.

### Arm 3 — decorator anchors

The rule under test: a decorated `def` is listed in the facts, and accepted as a surface, at its whole span — `app/routers/orders.py#L40-L49`, the decorator through the last line of the body — so every line of a handler is a surface's own line and a requirement anywhere in it passes the anchor gate. The other arm lists and anchors the decorator through the `def` line alone (`#L40-L41`, `decorate` in `survey/parse/walk.rs` handed the head's lines), so a requirement inside a handler must land at a decision point, a `return`, a call through a package, or a step into the tree, as a requirement inside a registration's named handler must today.

- **Whole `def` (the baseline card).** Recall as the baseline; the restem and surface figures the same on both arms, since the stem and the id derive from the decorator and the route, which both arms read whole; the risk is a requirement anchored at a line that only wires inside a handler, which the prompt refuses in words and the gate cannot.
- **Decorator-plus-head.** One correction round more on some seams — a requirement re-anchored from a wiring line to the decision it states — and recall within one of the baseline on each case, with `fastapi-routers` and `django-shop` the cases where it may fall by two, since their handlers are the longest; `(entry, stem)` `Stability` identical; the anchors a requirement lands on more often at a decision point than at a handler's head.

Decision rule: the head arm replaces the whole-`def` rule when recall is within one requirement of the baseline on every case and at least one case's requirements move off handler heads onto the decisions they state (read from the misses-by-anchor and the matched anchors in the card); the whole `def` stays when the head arm costs a `budget exhausted` run or two requirements on any case.

## The documentation survey experiment

The hypothesis the `typescript` rounds confirmed for code, put to prose: a documentation tree has **subjects** the way a codebase has surfaces — a feature, a resource, a flow a reviewer would put a heading over — and the model should name each one and anchor it at the heading, or the first line, that introduces it, while code derives the rest: the span to the next subject's anchor, the seam, and (under a second feature) the rule-bearing lines a `requirement` may anchor at. A directory is the wrong unit — one subject spans files and one file holds several — and a stem is the **domain noun** the documents spell, in kebab-case, never a file's or a directory's name and never the code's spelling; whether a document's stems agree with the code's is observed, never a target, since literal agreement between sources is the kind of match that misses what semantic matching would find. The corollary is the engine's: its grouping turn merges document and code claims into one requirement per behaviour with the right `status`, and the one literal rule it keeps — byte-equal ids pre-merged before the turn and never split after (`basis.rs` `baseline`) — is a risk to count, not a signal to design toward.

The eval was generalised first (the `[[source]]` table, per-source items, `[[decision]]`, `[[behaviour]]` grading, staging and `RUST_LOG` per adapter — [evals/README.md](../README.md)), the nine `typescript` and `python` cards before this section staying readable under it, and the eleven cases were written before any run: six documentation cases — `orders-doc`, `stories`, `adr`, `narrative`, `cross-cut`, `nestjs-docs` — and five cross-source cases — `orders-triad`, `orders-divergence`, `orders-conflict`, `orders-spelled`, `nestjs-pair` — each described in the eval README. The control is the shipped `documentation` component as it stands: an inline value is one seam, a tree is listed and cut by its top-level directories (a directory under two files folded into the root's own group, that group joined to the first directory when it is under two, a directory over sixteen files cut once more by its subdirectories), fewer than two seams collapse to one over the whole tree, and no seam holds a stem, so every id is the model's under `extract.md`'s one sentence that ids lead with the domain noun. The treatment arms are feature-gated on `sources/documentation`, as the survey-by-model arm was — `model-survey` (E1): a `prepare` that lists the documents and reads each one's outline by hand, one survey turn through `emery_sdk::survey::surfaces` under a `survey.md`, every document a subject's entry or `unreached`, spans built from the anchors, one seam over every document within `INLINE_BYTES` with every stem held or one seam per stem past it, an empty inventory falling to the directory cut; and `anchors` (E2, requiring it): the paragraphs, list items, table rows, Gherkin steps, and blockquotes inside each subject's span as `Seam::anchors`, never a heading, a fence, or front matter. The protocol's off-arm rule is read the other way here, as it was for the first experiment: the treatment is new code rather than a rule under test, so the feature flag is the arm and the default build is the control, and nothing is adopted by this round. Every run is the shipped `emery` built from the engine revision the adapters' SDK is pinned to (`dde48b65`, `emery 0.38.0`, from a detached worktree, since the engine checkout's head was mid-refactor), over components built from this tree into `target/eval/arms/<arm>/` so a later arm's build cannot overwrite an earlier one's. Three runs a case under `composer-2.5`, the synthesis arm once more under `gpt-5.3-codex`.

### Recommendations

Nothing is adopted by this round — the features stay off, the directory cut ships — and these are the recommendations the cards support.

1. **Keep the subject survey as the direction, and fix the grain before it ships.** The model names subjects in prose, headless prose included, and where a directory is not a subject the survey fixes what the cut cannot (`adr`, `narrative`, `cross-cut`, `nestjs-docs`); where a directory already is one, the model names each story or section a subject of its own on one run and the directory's noun on the next. The instability is in the grain of the noun, not in the naming, and two readings of it are open: `survey.md`'s one sentence on domain nouns did not settle the grain under `composer-2.5` and settled it under `gpt-5.3-codex` (exact on fifteen runs of fifteen), so the next arm is a prompt with the grain stated — one subject's noun is what a reader would file its rules under, a story and a section are its parts and never their own — graded on `orders-doc` and `stories` for `1 distinct` and ≥ 80% by pair against E1's `2 distinct` / `3 distinct`; or the grain is code's and not the model's — a subject is lowered to its document's or its directory's noun where the survey names several under one document, the way `typescript`'s derivation overrides the survey's stem with the one the code spells. The second trades the finding that `reference/accounts.md` holds three subjects for stability; the first keeps it and may not hold. Run the first before the second.
2. **Drop the structure-anchor gate as an arm; keep the reader.** Under this model and prompt no requirement anchors at a heading with or without the gate, so `anchors` buys nothing and costs the list it lays. The Markdown reader behind it (`survey/structure.rs`) is what the survey's facts and spans rest on and stays with `model-survey`.
3. **State the kind rule once, in the prompt, for a documentation tree's lists and decisions.** Two collapses in thirty-six treatment runs were kind choices, not anchor or span errors: `adr` run 1 of E2 claiming no `decision`, `adr` run 3 of E1 claiming each record's decision paragraph as a `decision` alone and no requirement at its rules; the checkpoint's own fix was of the same kind (a bullet list under a rule read as requirements). The seam text's "state each rule once" invites the model to choose one kind for a paragraph that is both a decision and the rules it decides; the prompt should say a decision record yields both.
4. **Give the authority rule a reading of agreement in other words.** The engine's corollary — doc and code claims merged into one requirement with the right status — is within reach: the grouping turn merges finer claims and the planted divergences are found 5 of 6 times under the treatment. What stands in the way is `basis.rs` reading every wording difference across kinds as `divergence`, so a merged requirement on an agreeing case is marked as if it disagreed, and a reader cannot tell `orders-triad`'s three from `orders-divergence`'s two. That is an engine experiment with its own rule — on `orders-triad`, divergences 0 with the two planted ones on `orders-divergence` still found — and the two multi-source cases' statuses are what it is graded on; it is out of this round's scope and is the next one's first arm.
5. **Count the brief.** The one pre-merge the control showed was `intent` ↔ `documentation`, not document ↔ code: an inline brief's ids are the model's and short (`orders.place`), and coincide by the byte with a document's. The byte-equal rule did no harm here — the brief and the document agreed — but it is the one place literal matching was seen to act, and a case with a brief that disagrees with the document under a shared id would show whether the pre-merge hides a conflict. Write it before the next round.
6. **Read the cases' own lesson.** `orders-api.md#L17`, "the order id is opaque to clients", reads as a missed behaviour on every treatment run of `orders-triad` and `orders-divergence` and on four control runs of six — and the line was claimed on every one of them, as a `criterion` of the placing rule (`orders.placing-an-order.place.opaque-id`), which is the kind the checkpoint's own fix tells the model a sentence's aside is. The behaviour grader reads requirement citations alone, so a behaviour the model states as a criterion is a miss by construction. Either the expected behaviour names the kind it accepts, or the grader reads a criterion's anchor as meeting a behaviour under its requirement; the expected set, not the arm, is what the miss indicts.

## The build arm

The first live run of `emery build`, and the instrument for it: the engine's build in waves ([augentic/emery](https://github.com/augentic/emery), `crates/engine/src/build.rs`) over the `typescript-target` component ([targets/typescript-target](../../targets/typescript-target/)), the one target this tree ships, through the runner's `--build` mode ([evals/README.md](../README.md#building-the-plan)). Each case is specified as before, then its plan is built into a greenfield repository the runner lays beside the sources — bare, one root commit — under the engine's default width, and the card gains five columns (`built`, `verified`, `build wall`, `speedup`, `covered`) and the build's notes: each wave's slices as they merged, the conflicts, the verify's refusals, the uncovered ids, and the chain read back from the repository with the host's git. The question is phase 3's, and the measurement is written to answer it item by item: whether a failed wave needs bisecting to its slice, whether integrating as each slice finishes would beat the wave, whether a conflict the merge rules cannot hold needs a `resolve` turn, and whether the model's shell ever seals a commit of its own — the head check the engine now runs at integration, `server_error` where a slice's working copy no longer sits on the commit it was cut at.

Two cases, one run each, `composer-2.5` pinned, as the two ends [the plan widths](#the-plan-widths) measured: `express-orders`, four slices in three waves (`2/1/1` on 3 of 4 plans, serial ÷ waves 1.33), the small case that should land; and `nestjs-pair`, the widest real codebase in the set (9–19 slices in 5–9 waves, 3–7 wide, serial ÷ waves 1.29–2.8), the case a wave-level failure is likeliest on. One run each because a build turn is minutes and a wide plan is an hour, and because the first question — does the build land at all — is answered by one run and the rest are read from its notes rather than decided.

### Predictions

- **Landing.** `express-orders` lands: every slice merged, every wave verified, `emery/<revision>` pushed to `origin` and read back from `target.git` as a first-parent chain naming each slice once in its `Slice:` trailer. `nestjs-pair` does not land on its run: a `verify-failed` on a wave of two or more slices — `tsc` refusing a tree where two slices typed one name differently, or a test importing a module another slice owns — or a `slice-conflict`; `express-orders` may fail the same way on its two-wide first wave, and lands when it does not.
- **Conflicts.** Where a wave is wider than one, a conflict at `package.json` on at least one wave of `nestjs-pair` — two slices each adding a dependency or a script to the one manifest no rule holds, the layout's own signal — and none at `src/index.ts`, the union rule keeping both slices' `export * as` lines, nor at `package-lock.json`, `ours` keeping the integrated side's. A conflict is read as `-1` where its slice merged on its second build, over the merged head, and as `!1` where the second build conflicted too.
- **Speedup.** The measured speedup is at or under the plan's own factor on both — 1.0–1.3× against 1.33 on `express-orders`, 1.2–2.0× against the plan's 1.3–2.8 on `nestjs-pair` — since the critical path takes each wave at its slowest slice and adds the verify, both of which the plan's factor assumes away; the per-wave build durations in the notes spread 2× or more within a wave on `nestjs-pair`.
- **Coverage.** `covered` is 90% or more of the merged slices' requirements on both; an uncovered id is one the model judged outside the slice's reach — a deployment, a database, an external system the greenfield tree has no stand-in for — never a requirement the report invented.
- **The head check.** No `server_error` from it: the build prompt runs its checks through the shell and never git, so every slice's copy still sits where it was cut at integration.
- **Budget.** A build turn runs 2–8 minutes a slice under `composer-2.5`, the install, type check, and test loop inside it; a verify 1–3 minutes; nothing `timeout`s at 600/120 on `express-orders`, and `nestjs-pair`'s widest wave is the one at risk. The whole build is 10–25 minutes on `express-orders` and 40–90 minutes on `nestjs-pair`.
- **Observed, never decided on:** the build's tokens, the files each slice writes, and how the model spells the modules.

### Decision rule

- **The build is real** when `express-orders` lands with its label pushed and the chain read back from `target.git` names each slice once with its trailers — the instrument's own check, and nothing below is read until it holds. A `server_error` from the report gate or a build turn that writes nothing is the adapter's defect, fixed before anything is read.
- **Bisecting a failed wave is asked for** when a `verify-failed` lands on a wave of two or more slices, so the wave names the failure and no slice does — the figure is the failed wave's width in its `- wave k:` note. A `verify-failed` on a one-slice wave, or none at all, asks for nothing a bisect would give.
- **Rolling integration is asked for** when the measured speedup on `nestjs-pair` falls under the plan's factor by more than a third, the wave held by its slowest slice while the rest wait — read from the per-wave build durations in the notes. Within a third, waves are enough at this width.
- **A `resolve` turn is asked for** when a conflict lands at a path no rule can hold — `package.json` — on either case, since the second build's `!1` is a run ended. A conflict at `src/index.ts` is the union rule or the layout wrong, the adapter's fix and no engine item. No conflict on two runs says nothing about conflicts.
- **`emery:exec` is asked for** by a head-check `server_error` on any slice; none keeps it unbuilt, as the plan has it.
- **The plan's factor is read as an upper bound** from here: a `speedup` column at or under it on both cases confirms the plan-widths reading that the width pays on the large plans alone, and the figure the next slicing arm is graded against is the measured one.

**Decision, the build is real.** It holds: `express-orders` landed with its label pushed, and the chain read back from `target.git` names each slice once with its trailers, the merges in wave order; the figures below are read.

**Decision, bisect.** Not asked for by this data: every verify passed, on the one-slice waves and on the first wave's one integrated slice alike, so no wave named a failure for a bisect to find a slice in. It stays unbuilt until a `verify-failed` lands on a wave of two or more.

**Decision, rolling integration.** Not asked for: the measured speedup fell under the plan's factor (1.05× against 1.33×), but not by the wave's slowest slice holding the rest — the one two-wide wave's builds were 64 s and 91 s — and by two things rolling integration does not touch: the verify, half the serial time, paid once a wave whatever the width; and the conflict, which threw a build away and added a wave. The reading of the plan widths stands: the width pays on the large plans, and this run could not reach one.

**Decision, `resolve`.** Asked for in the weak form the rule allowed and no more: the conflict landed at `package.json`, the path no rule can hold, and the second build over the merged head resolved it, so the `-1` is the cost — a build thrown away and a wave added — and no `!1` ended a run. The adapter's layout did its part (`src/index.ts` under union, the manifests byte-identical where both slices laid them); the one manifest two slices add dependencies to is where a `resolve` turn, or a layout rule that puts a slice's dependencies somewhere the union rule can hold, would pay. Two runs say nothing about how often.

**Decision, `emery:exec`.** Not asked for: no head-check `server_error` on either case; the model ran its checks through the shell and never git.

**What the run asked for instead.** The tool-call budget. Thirty-two guest-tool calls a completion, one file a `write_file` call, bounds a slice to some twenty-eight files after its `list_docs` and `read_doc` reads, and the wide case's slices want more under this model: `architecture` 17 files on one run and 30 on the next, `start` more than 19. `express-orders` cleared the ceiling with 8–25 writes a slice, and its `orders` slice's correction round — a file written and left out of `written` — spent calls the same budget counts. The item is upstream of every phase 3 mechanism: no conflict, verify, or speedup figure exists for a plan whose first wave cannot report, and it is neither bisect nor rolling nor `resolve`. Three remedies, none adopted here: the budget raised or made the deployment's — `Limits::max_tool_calls` is the host's default with no knob, and the Cursor backend could carry one; the SDK's `write_file` taking several files a call, so a slice's tree is one call rather than thirty; or the slicing turn cutting narrower slices where a stem's requirements run past twenty, which the `start` and `orders` slices of both plans do. **What it says for phase 3.** The build is real on the small plan and bounded by the write path on the large one. The `speedup` column is read against the plan's factor as an upper bound from here, and the next card over `nestjs-pair` runs once the write path is widened.

## The write path

The three remedies the build arm asked for, landed together and measured by the re-run it could not reach: the tool-call budget as the Cursor backend's (`CURSOR_MAX_TOOL_CALLS`, default `128`, in [augentic/omnia-backends](https://github.com/augentic/omnia-backends) `crates/cursor`, answered to the host through `WasiModelCtx::limits` in place of `wasi-model`'s 32); the SDK's `write_files` in place of `write_file` (one or more files a call, every path held to the root-relative rule before the first write, a refused call writing nothing; [augentic/emery](https://github.com/augentic/emery) `crates/sdk/src/target/write.rs`), with [targets/typescript-target](../../targets/typescript-target/) `build.md` saying to lay the module, entry line, test, and manifests in one call; and the slicing floor moved under an oversized stem — a stem of more than `SLICE_CAP` (20) requirements is listed to the slicing turn by its sub-stems, the first two segments of its ids, and the gate admits a split along them and refuses one through them (`crates/engine/src/specify/plan.rs`), so the `start` and `orders` slices of both plans, 25 and 58 requirements, are now the model's to cut. The runner inherits `CURSOR_MAX_TOOL_CALLS` and the card's header names it when set, so each card says which budget it ran under.

The same two cases as the build arm, one run each, `composer-2.5` pinned: `cargo run -p evals -- --build nestjs-pair express-orders`. The budget is the default, 128, raised in no run; a run that exhausts it is the datum, not a rung to climb. `express-orders` is the control: it landed under the old path, and its figures say what the batched write and the sub-stem floor cost or save on a plan the budget never bounded.

### Predictions

- **The budget.** Both wave-1 slices of `nestjs-pair` report under 128: `architecture` and `start` each end in a `Report` rather than `budget exhausted`, the SDK's gate accepting it or sending it back once. No slice of either case spends more than 40 tool calls — the reference reads, the writes, and the corrections together — since a slice's tree is now one to three `write_files` calls (the module and its tests laid together, a fix loop rewriting a file or two after) in place of 17–30 `write_file` calls. A slice that still exhausts 128 is the model writing one file a call against the prompt, read in its `write_files` calls' file counts, and the prompt's defect, not the budget's.
- **The calls.** `write_files` calls per slice 1–4, median 2, on both cases, the first call carrying 70% or more of the slice's files; a later call carries one to three files the loop rewrote. A call refused whole — a path outside the root or under `.emery/` — on no slice.
- **The plan.** `nestjs-pair`'s specification slices under the sub-stem floor into more slices than the `2/4/2/1/1/1` of the build arm's card: 13–18 slices in 6–8 waves, the `start` stem (25 requirements) cut into two or three slices along its sub-stems and the model's `depends-on` putting them in one wave or a chain of two; `express-orders`' `orders` stem (58 requirements, the one slice the build arm wrote 19 files and 242 s for) cut into two to four, so its plan is 5–7 slices in 3–4 waves and its factor rises above 1.33. No slice of more than 25 requirements on either plan; a sub-stem itself past the cap, which the gate allows, on none, since no second segment of either specification holds more than 20 ids.
- **Landing.** `express-orders` lands again: every slice merged, every wave verified, the label pushed, the chain read back naming each slice once — the control's check, read before anything else. `nestjs-pair` reaches at least its third wave with every slice of waves 1 and 2 reporting; whether it lands turns on the build arm's original predictions, which stand unchanged for it: a `verify-failed` on a wave of two or more slices, or a `slice-conflict` at `package.json`, is the likeliest end.
- **Speedup.** `express-orders` 1.0–1.4× against its new plan's factor, the finer `orders` cut giving the two-wide waves something to run beside; `nestjs-pair`, where it lands, 1.2–2.0× against the plan's, the verify still the fixed cost a wave. The plan's factor is the upper bound, as the build arm set it.
- **Coverage and the head check.** As the build arm predicted: `covered` 90% or more of the merged slices' requirements, no head-check `server_error`.
- **Observed, never decided on:** the tokens, the bytes a `write_files` call carries, and how many files a slice writes in all against the build arm's 8–25.

### Decision rule

- **The write path fits** when every wave-1 slice of `nestjs-pair` reports — the figure is the run's `budget exhausted` count, zero — and `express-orders` lands as before. One `budget exhausted` with the slice's `write_files` calls carrying one file each is the prompt's item; one with its calls carrying several files is the budget's, and `CURSOR_MAX_TOOL_CALLS` is raised for the next card and recorded in its header.
- **The sub-stem floor is read on the plan columns.** `slices` and `waves` against the build arm's `4 (2/1/1)` and `11 (2/4/2/1/1/1)`: a plan whose oversized stem split along its sub-stems is the rule working; one that kept the stem whole is the model's choice under the brief, allowed by the gate, and the brief's wording is the item. A slice refused for a sub-stem split, in the engine's `slicing` correction, is the model misreading the floor and a `slicing.md` item.
- **The build arm's rule applies from wave 2 on.** Once wave 1 reports, each of its four decisions — bisect, rolling integration, `resolve`, `emery:exec` — is read exactly as [the build arm](#the-build-arm) wrote it, over the waves this run reaches; this section decides nothing of them.
- **The control must hold.** An `express-orders` that no longer lands, or whose build turns run slower than the build arm's 64–242 s by more than half, is the batched write or the finer cut costing what it was meant to save, and that is the first item, read before any `nestjs-pair` figure.
