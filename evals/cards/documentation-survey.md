# The documentation survey

A round of the eval, run and read under [the protocol](README.md#protocol); [the README](README.md#rounds) indexes every round.

## The documentation survey experiment

The hypothesis the `typescript` rounds confirmed for code, put to prose: a documentation tree has **subjects** the way a codebase has surfaces — a feature, a resource, a flow a reviewer would put a heading over — and the model should name each one and anchor it at the heading, or the first line, that introduces it, while code derives the rest: the span to the next subject's anchor, the seam, and (under a second feature) the rule-bearing lines a `requirement` may anchor at. A directory is the wrong unit — one subject spans files and one file holds several — and a stem is the **domain noun** the documents spell, in kebab-case, never a file's or a directory's name and never the code's spelling; whether a document's stems agree with the code's is observed, never a target, since literal agreement between sources is the kind of match that misses what semantic matching would find. The corollary is the engine's: its grouping turn merges document and code claims into one requirement per behaviour with the right `status`, and the one literal rule it keeps — byte-equal ids pre-merged before the turn and never split after (`basis.rs` `baseline`) — is a risk to count, not a signal to design toward.

The eval was generalised first (the `[[source]]` table, per-source items, `[[decision]]`, `[[behaviour]]` grading, staging and `RUST_LOG` per adapter — [evals/README.md](../README.md)), the nine `typescript` and `python` cards before it staying readable under it, and the eleven cases were written before any run: six documentation cases — `orders-doc`, `stories`, `adr`, `narrative`, `cross-cut`, `nestjs-docs` — and five cross-source cases — `orders-triad`, `orders-divergence`, `orders-conflict`, `orders-spelled`, `nestjs-pair` — each described in the eval README. The control is the shipped `documentation` component as it stands: an inline value is one seam, a tree is listed and cut by its top-level directories (a directory under two files folded into the root's own group, that group joined to the first directory when it is under two, a directory over sixteen files cut once more by its subdirectories), fewer than two seams collapse to one over the whole tree, and no seam holds a stem, so every id is the model's under `extract.md`'s one sentence that ids lead with the domain noun. The treatment arms are feature-gated on `sources/documentation`, as the survey-by-model arm was — `model-survey` (E1): a `prepare` that lists the documents and reads each one's outline by hand, one survey turn through `emery_sdk::survey::surfaces` under a `survey.md`, every document a subject's entry or `unreached`, spans built from the anchors, one seam over every document within `INLINE_BYTES` with every stem held or one seam per stem past it, an empty inventory falling to the directory cut; and `anchors` (E2, requiring it): the paragraphs, list items, table rows, Gherkin steps, and blockquotes inside each subject's span as `Seam::anchors`, never a heading, a fence, or front matter. The protocol's off-arm rule is read the other way here, as it was for the first experiment: the treatment is new code rather than a rule under test, so the feature flag is the arm and the default build is the control, and nothing is adopted by this round. Every run is the shipped `emery` built from the engine revision the adapters' SDK is pinned to (`dde48b65`, `emery 0.38.0`, from a detached worktree, since the engine checkout's head was mid-refactor), over components built from this tree into `target/eval/arms/<arm>/` so a later arm's build cannot overwrite an earlier one's. Three runs a case under `composer-2.5`, the synthesis arm once more under `gpt-5.3-codex`.

One run of the control over `orders-doc` (`EVAL_RUNS=1`, `23-59-32Z`, not copied in) preceded this section as the pipeline's smoke test — exit 0 in 46 s, 4/4 and 3/3, stem `orders` — and nothing else had been read when the predictions below were written; the baseline card was running as they were.

### Decision rule

- **E1 — the subject survey wins** when stem sets are `1 distinct` across the three runs on at least five of the six documentation cases, subjects by `(entry, stem)` ≥ 80% on each case, and requirement recall within one of the control on each — while the control shows `> 1 distinct` stem sets or the same behaviour claimed from two seams on `cross-cut`. `narrative` decides one of two findings, either of which stands: the model names subjects there and recall holds, or the empty-inventory fallback is what stands for headless prose. **The control wins** when stem sets differ across runs on two or more cases despite the convention `survey.md` states — naming prose needs more than a prompt.
- **E2 — structure anchors stand** when heading-anchored requirements drop to zero, recall sits within one of E1 on each case, and no run is exhausted by the anchor gate; an exhaustion indicts the anchor set and sends it back for rework, as the function-heads card did, and decides nothing against the idea.
- **E3 — the synthesis holds** when behaviours met ≥ 90% over the five cases, splits ≤ 1 a case, wrong merges 0, the three planted statuses met (`divergence` ×2 with the document winning and the code the loser note, `conflict` ×1), cross-source pre-merges 0 on `orders-triad` and counted on `orders-spelled` — and `orders-spelled` not better than `orders-triad` by more than one behaviour, else literal id equality is carrying the merge and the byte-equal rule is doing the grouping's work. `nestjs-pair`'s split count is read against the prediction that it fails the clause under every arm: a failure there alone is the scale finding, not the arm's.
- **Observed, never decided on:** document–code stem agreement, the budget ladder, and tokens and wall time per arm. Recall is read as a band throughout, never alone.

### Checkpoint

One `EVAL_RUNS=1` pass an arm over `orders-doc`, `cross-cut`, and `narrative` (`01-13-45Z` for `model-survey`, `01-24-07Z` for `anchors`, neither copied in), read for defects of the mechanism before the graded runs. The survey turn ran once on every case under both arms — 16–23 s, 10–62 K input tokens, no correction round — and its facts laid what the outline reads: every heading at its line for the twenty `cross-cut` documents, `no heading; opens at L1: …` for the three `narrative` pieces. The model named three subjects at `orders-doc`'s three `##` headings under `orders`, three at `narrative`'s three first lines as `bookings`, `membership`, `returns` — exact, where the prediction had it drifting — and twenty on `cross-cut` with the four index documents `unreached`, `returns` one subject across its three documents, `reference/accounts.md` three; code cut one seam over each of the small trees and ten, one per stem, over `cross-cut`, no seam's extraction turn was corrected, and under `anchors` not one requirement was sent back to re-anchor. Requirement recall 4/4, 19/19, 48/48 on both arms. Two of the model's readings differ from the expected set and stand as its judgement, not a defect: `policies/fair-use.md` is its own subject under `fair-use` where the case expects `loans`, and `guides/getting-started.md` is two subjects — `Joining Toolshed` under `membership`, `Your first loan` under `loans` — where the case expects one. One defect, fixed and the arms rebuilt (`model-survey` `73ca5bb9d6fc9a66`, `anchors` `245505c5ea734cda`, by sha256 prefix): `cross-cut`'s three criteria — the bullet list under "Keeping a membership" — came back 0/3 on both arms where the control had them 3/3 on two runs of three, each claimed as a `requirement` at the right lines. ### Recommendations

Nothing is adopted by this round — the features stay off, the directory cut ships — and these are the recommendations the cards support.

1. **Keep the subject survey as the direction, and fix the grain before it ships.** The model names subjects in prose, headless prose included, and where a directory is not a subject the survey fixes what the cut cannot (`adr`, `narrative`, `cross-cut`, `nestjs-docs`); where a directory already is one, the model names each story or section a subject of its own on one run and the directory's noun on the next. The instability is in the grain of the noun, not in the naming, and two readings of it are open: `survey.md`'s one sentence on domain nouns did not settle the grain under `composer-2.5` and settled it under `gpt-5.3-codex` (exact on fifteen runs of fifteen), so the next arm is a prompt with the grain stated — one subject's noun is what a reader would file its rules under, a story and a section are its parts and never their own — graded on `orders-doc` and `stories` for `1 distinct` and ≥ 80% by pair against E1's `2 distinct` / `3 distinct`; or the grain is code's and not the model's — a subject is lowered to its document's or its directory's noun where the survey names several under one document, the way `typescript`'s derivation overrides the survey's stem with the one the code spells. The second trades the finding that `reference/accounts.md` holds three subjects for stability; the first keeps it and may not hold. Run the first before the second.
2. **Drop the structure-anchor gate as an arm; keep the reader.** Under this model and prompt no requirement anchors at a heading with or without the gate, so `anchors` buys nothing and costs the list it lays. The Markdown reader behind it (`survey/structure.rs`) is what the survey's facts and spans rest on and stays with `model-survey`.
3. **State the kind rule once, in the prompt, for a documentation tree's lists and decisions.** Two collapses in thirty-six treatment runs were kind choices, not anchor or span errors: `adr` run 1 of E2 claiming no `decision`, `adr` run 3 of E1 claiming each record's decision paragraph as a `decision` alone and no requirement at its rules; the checkpoint's own fix was of the same kind (a bullet list under a rule read as requirements). The seam text's "state each rule once" invites the model to choose one kind for a paragraph that is both a decision and the rules it decides; the prompt should say a decision record yields both.
4. **Give the authority rule a reading of agreement in other words.** The engine's corollary — doc and code claims merged into one requirement with the right status — is within reach: the grouping turn merges finer claims and the planted divergences are found 5 of 6 times under the treatment. What stands in the way is `basis.rs` reading every wording difference across kinds as `divergence`, so a merged requirement on an agreeing case is marked as if it disagreed, and a reader cannot tell `orders-triad`'s three from `orders-divergence`'s two. That is an engine experiment with its own rule — on `orders-triad`, divergences 0 with the two planted ones on `orders-divergence` still found — and the two multi-source cases' statuses are what it is graded on; it is out of this round's scope and is the next one's first arm.
5. **Count the brief.** The one pre-merge the control showed was `intent` ↔ `documentation`, not document ↔ code: an inline brief's ids are the model's and short (`orders.place`), and coincide by the byte with a document's. The byte-equal rule did no harm here — the brief and the document agreed — but it is the one place literal matching was seen to act, and a case with a brief that disagrees with the document under a shared id would show whether the pre-merge hides a conflict. Write it before the next round.
6. **Read the cases' own lesson.** `orders-api.md#L17`, "the order id is opaque to clients", reads as a missed behaviour on every treatment run of `orders-triad` and `orders-divergence` and on four control runs of six — and the line was claimed on every one of them, as a `criterion` of the placing rule (`orders.placing-an-order.place.opaque-id`), which is the kind the checkpoint's own fix tells the model a sentence's aside is. The behaviour grader reads requirement citations alone, so a behaviour the model states as a criterion is a miss by construction. Either the expected behaviour names the kind it accepts, or the grader reads a criterion's anchor as meeting a behaviour under its requirement; the expected set, not the arm, is what the miss indicts.
