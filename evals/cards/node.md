# The build through `node`

A round of the eval, run and read under [the protocol](README.md#protocol); [the README](README.md#rounds) indexes every round.

## The build arm

The first live run of `emery build`, and the instrument for it: the engine's build in waves ([augentic/emery](https://github.com/augentic/emery), `crates/engine/src/build.rs`) over the `node` component ([targets/node](../../targets/node/)), the one target this tree ships, through the runner's `--build` mode ([evals/README.md](../README.md#building-the-plan)). Each case is specified as before, then its plan is built into a greenfield repository the runner lays beside the sources — bare, one root commit — under the engine's default width, and the card gains five columns (`built`, `verified`, `build wall`, `speedup`, `covered`) and the build's notes: each wave's slices as they merged, the conflicts, the verify's refusals, the uncovered ids, and the chain read back from the repository with the host's git. The question is phase 3's, and the measurement is written to answer it item by item: whether a failed wave needs bisecting to its slice, whether integrating as each slice finishes would beat the wave, whether a conflict the merge rules cannot hold needs a `resolve` turn, and whether the model's shell ever seals a commit of its own — the head check the engine now runs at integration, `server_error` where a slice's working copy no longer sits on the commit it was cut at.

Two cases, one run each, `composer-2.5` pinned, as the two ends [the plan widths](plan-widths.md) measured: `express-orders`, four slices in three waves (`2/1/1` on 3 of 4 plans, serial ÷ waves 1.33), the small case that should land; and `nestjs-pair`, the widest real codebase in the set (9–19 slices in 5–9 waves, 3–7 wide, serial ÷ waves 1.29–2.8), the case a wave-level failure is likeliest on. One run each because a build turn is minutes and a wide plan is an hour, and because the first question — does the build land at all — is answered by one run and the rest are read from its notes rather than decided.

### Predictions

- **Landing.** `express-orders` lands: every slice merged, every wave verified, `emery/<revision>` pushed to `origin` and read back from `target.git` as a first-parent chain naming each slice once in its `Slice:` trailer. `nestjs-pair` does not land on its run: a `verify-failed` on a wave of two or more slices — `tsc` refusing a tree where two slices typed one name differently, or a test importing a module another slice owns — or a `slice-conflict`; `express-orders` may fail the same way on its two-wide first wave, and lands when it does not.
- **Conflicts.** Where a wave is wider than one, a conflict at `package.json` on at least one wave of `nestjs-pair` — two slices each adding a dependency or a script to the one manifest no rule holds, the layout's own signal — and none at `src/index.ts`, the union rule keeping both slices' `export * as` lines, nor at `package-lock.json`, `ours` keeping the integrated side's. A conflict is read as `-1` where its slice merged on its second build, over the merged head, and as `!1` where the second build conflicted too.
- **Speedup.** The measured speedup is at or under the plan's own factor on both — 1.0–1.3× against 1.33 on `express-orders`, 1.2–2.0× against the plan's 1.3–2.8 on `nestjs-pair` — since the critical path takes each wave at its slowest slice and adds the verify, both of which the plan's factor assumes away; the per-wave build durations in the notes spread 2× or more within a wave on `nestjs-pair`.
- **Coverage.** `covered` is 90% or more of the merged slices' requirements on both; an uncovered id is one the model judged outside the slice's reach — a deployment, a database, an external system the greenfield tree has no stand-in for — never a requirement the report invented.
- **The head check.** No `server_error` from it: the build prompt runs its checks through the shell and never git, so every slice's copy still sits where it was cut at integration.
- **Budget.** A build turn runs 2–8 minutes a slice under `composer-2.5`, the install, type check, and test loop inside it; a verify 1–3 minutes; nothing `timeout`s at 600/120 on `express-orders`, and `nestjs-pair`'s widest wave is the one at risk. The whole build is 10–25 minutes on `express-orders` and 40–90 minutes on `nestjs-pair`.
- **Observed, never decided on:** the build's tokens, the files each slice writes, and how the model spells the modules.

### Decision rule

- **The build is real** when `express-orders` lands with its label pushed and the chain read back from `target.git` names each slice once with its trailers — the instrument's own check, and nothing below is read until it holds. A `server_error` from the report gate or a build turn that writes nothing is the adapter's defect, fixed before anything is read.
- **Bisecting a failed wave is asked for** when a `verify-failed` lands on a wave of two or more slices, so the wave names the failure and no slice does — the figure is the failed wave's width in its `- wave k:` note. A `verify-failed` on a one-slice wave, or none at all, asks for nothing a bisect would give.
- **Rolling integration is asked for** when the measured speedup on `nestjs-pair` falls under the plan's factor by more than a third, the wave held by its slowest slice while the rest wait — read from the per-wave build durations in the notes. Within a third, waves are enough at this width.
- **A `resolve` turn is asked for** when a conflict lands at a path no rule can hold — `package.json` — on either case, since the second build's `!1` is a run ended. A conflict at `src/index.ts` is the union rule or the layout wrong, the adapter's fix and no engine item. No conflict on two runs says nothing about conflicts.
- **`emery:exec` is asked for** by a head-check `server_error` on any slice; none keeps it unbuilt, as the plan has it.
- **The plan's factor is read as an upper bound** from here: a `speedup` column at or under it on both cases confirms the plan-widths reading that the width pays on the large plans alone, and the figure the next slicing arm is graded against is the measured one.

**Decision, the build is real.** It holds: `express-orders` landed with its label pushed, and the chain read back from `target.git` names each slice once with its trailers, the merges in wave order; the figures below are read.

**Decision, bisect.** Not asked for by this data: every verify passed, on the one-slice waves and on the first wave's one integrated slice alike, so no wave named a failure for a bisect to find a slice in. It stays unbuilt until a `verify-failed` lands on a wave of two or more.

**Decision, rolling integration.** Not asked for: the measured speedup fell under the plan's factor (1.05× against 1.33×), but not by the wave's slowest slice holding the rest — the one two-wide wave's builds were 64 s and 91 s — and by two things rolling integration does not touch: the verify, half the serial time, paid once a wave whatever the width; and the conflict, which threw a build away and added a wave. The reading of the plan widths stands: the width pays on the large plans, and this run could not reach one.

**Decision, `resolve`.** Asked for in the weak form the rule allowed and no more: the conflict landed at `package.json`, the path no rule can hold, and the second build over the merged head resolved it, so the `-1` is the cost — a build thrown away and a wave added — and no `!1` ended a run. The adapter's layout did its part (`src/index.ts` under union, the manifests byte-identical where both slices laid them); the one manifest two slices add dependencies to is where a `resolve` turn, or a layout rule that puts a slice's dependencies somewhere the union rule can hold, would pay. Two runs say nothing about how often.

**Decision, `emery:exec`.** Not asked for: no head-check `server_error` on either case; the model ran its checks through the shell and never git.

**What the run asked for instead.** The tool-call budget. Thirty-two guest-tool calls a completion, one file a `write_file` call, bounds a slice to some twenty-eight files after its `list_docs` and `read_doc` reads, and the wide case's slices want more under this model: `architecture` 17 files on one run and 30 on the next, `start` more than 19. `express-orders` cleared the ceiling with 8–25 writes a slice, and its `orders` slice's correction round — a file written and left out of `written` — spent calls the same budget counts. The item is upstream of every phase 3 mechanism: no conflict, verify, or speedup figure exists for a plan whose first wave cannot report, and it is neither bisect nor rolling nor `resolve`. Three remedies, none adopted here: the budget raised or made the deployment's — `Limits::max_tool_calls` is the host's default with no knob, and the Cursor backend could carry one; the SDK's `write_file` taking several files a call, so a slice's tree is one call rather than thirty; or the slicing turn cutting narrower slices where a stem's requirements run past twenty, which the `start` and `orders` slices of both plans do. The first two are an engine or omnia change the next card tests; the third moves the plan widths this round measured.

**What it says for phase 3.** The build is real on the small plan and bounded by the write path on the large one, and none of the four items the arm was written to decide between is asked for by this card. What is asked for is a write path that fits a slice — the tool-call budget or a batched `write_file` — before any wide plan can be measured at all, and that is the first item of phase 3 from here; the conflict-at-the-manifest reading makes a `resolve` turn, or a dependency layout the union rule can hold, the second. The `speedup` column is read against the plan's factor as an upper bound from here, and the next card over `nestjs-pair` runs once the write path is widened.

## The write path

The three remedies the build arm asked for, landed together and measured by the re-run it could not reach: the tool-call budget as the Cursor backend's (`CURSOR_MAX_TOOL_CALLS`, default `128`, in [augentic/omnia-backends](https://github.com/augentic/omnia-backends) `crates/cursor`, answered to the host through `WasiModelCtx::limits` in place of `wasi-model`'s 32); the SDK's `write_files` in place of `write_file` (one or more files a call, every path held to the root-relative rule before the first write, a refused call writing nothing; [augentic/emery](https://github.com/augentic/emery) `crates/sdk/src/target/write.rs`), with [targets/node](../../targets/node/) `build.md` saying to lay the module, entry line, test, and manifests in one call; and the slicing floor moved under an oversized stem — a stem of more than `SLICE_CAP` (20) requirements is listed to the slicing turn by its sub-stems, the first two segments of its ids, and the gate admits a split along them and refuses one through them (`crates/engine/src/specify/plan.rs`), so the `start` and `orders` slices of both plans, 25 and 58 requirements, are now the model's to cut. The runner inherits `CURSOR_MAX_TOOL_CALLS` and the card's header names it when set, so each card says which budget it ran under.

The same two cases as the build arm, one run each, `composer-2.5` pinned: `cargo run -p evals -- --build nestjs-pair express-orders`. The budget is the default, 128, raised in no run; a run that exhausts it is the datum, not a rung to climb. `express-orders` is the control: it landed under the old path, and its figures say what the batched write and the sub-stem floor cost or save on a plan the budget never bounded.

### Predictions

- **The budget.** Both wave-1 slices of `nestjs-pair` report under 128: `architecture` and `start` each end in a `Report` rather than `budget exhausted`, the SDK's gate accepting it or sending it back once. No slice of either case spends more than 40 tool calls — the reference reads, the writes, and the corrections together — since a slice's tree is now one to three `write_files` calls (the module and its tests laid together, a fix loop rewriting a file or two after) in place of 17–30 `write_file` calls. A slice that still exhausts 128 is the model writing one file a call against the prompt, read in its `write_files` calls' file counts, and the prompt's defect, not the budget's.
- **The calls.** `write_files` calls per slice 1–4, median 2, on both cases, the first call carrying 70% or more of the slice's files; a later call carries one to three files the loop rewrote. A call refused whole — a path outside the root or under `.emery/` — on no slice.
- **The plan.** `nestjs-pair`'s specification slices under the sub-stem floor into more slices than the `2/4/2/1/1/1` of the build arm's card: 13–18 slices in 6–8 waves, the `start` stem (25 requirements) cut into two or three slices along its sub-stems and the model's `depends-on` putting them in one wave or a chain of two; `express-orders`' `orders` stem (58 requirements, the one slice the build arm wrote 19 files and 242 s for) cut into two to four, so its plan is 5–7 slices in 3–4 waves and its factor rises above 1.33. No slice of more than 25 requirements on either plan; a sub-stem itself past the cap, which the gate allows, on none, since no second segment of either specification holds more than 20 ids.
- **Landing.** `express-orders` lands again: every slice merged, every wave verified, the label pushed, the chain read back naming each slice once — the control's check, read before anything else. `nestjs-pair` reaches at least its third wave with every slice of waves 1 and 2 reporting; whether it lands turns on the build arm's original predictions, which stand unchanged for it: a `verify-failed` on a wave of two or more slices, or a `slice-conflict` at `package.json`, is the likeliest end.
- **Speedup.** `express-orders` 1.0–1.4× against its new plan's factor, the finer `orders` cut giving the two-wide waves something to run beside; `nestjs-pair`, where it lands, 1.2–2.0× against the plan's, the verify still the fixed cost a wave. The plan's factor is the upper bound, as the build arm set it.
- **Coverage and the head check.** As the build arm predicted: `covered` 90% or more of the merged slices' requirements, no head-check `server_error`.
- **Observed, never decided on:** the tokens, the bytes a `write_files` call carries, and how many files a slice writes in all against the build arm's 8–25.

### Decision rule

- **The write path fits** when every wave-1 slice of `nestjs-pair` reports — the figure is the run's `budget exhausted` count, zero — and `express-orders` lands as before. One `budget exhausted` with the slice's `write_files` calls carrying one file each is the prompt's item; one with its calls carrying several files is the budget's, and `CURSOR_MAX_TOOL_CALLS` is raised for the next card and recorded in its header.
- **The sub-stem floor is read on the plan columns.** `slices` and `waves` against the build arm's `4 (2/1/1)` and `11 (2/4/2/1/1/1)`: a plan whose oversized stem split along its sub-stems is the rule working; one that kept the stem whole is the model's choice under the brief, allowed by the gate, and the brief's wording is the item. A slice refused for a sub-stem split, in the engine's `slicing` correction, is the model misreading the floor and a `slicing.md` item.
- **The build arm's rule applies from wave 2 on.** Once wave 1 reports, each of its four decisions — bisect, rolling integration, `resolve`, `emery:exec` — is read exactly as [the build arm](#the-build-arm) wrote it, over the waves this run reaches; this section decides nothing of them.
- **The control must hold.** An `express-orders` that no longer lands, or whose build turns run slower than the build arm's 64–242 s by more than half, is the batched write or the finer cut costing what it was meant to save, and that is the first item, read before any `nestjs-pair` figure.

## The build loop

Phase 3's question put as hypotheses over the build step itself — the width a wave buys, the repair loop that holds a tree to its requirements, and what the verify is worth — each with an arm, a prediction, and a rule written here before any arm ran, under [the protocol](README.md#protocol). Every arm is one run a case, sequential, so the Cursor pool and the timings are never shared between two runs. The binary for every arm is the engine at `d0fddbad` built from a detached worktree with `omnia-cursor` taken from the sibling `omnia-backends` working tree, since the budget remedy (`CURSOR_MAX_TOOL_CALLS`, default 128) is written there and not yet released; the component is `node` at `9097958`, and the rebuild arms run the runner's temporary `--rebuild <card>` mode, which copies a card's staged project, deletes the label its build pushed, and builds the same committed revision again under this invocation's binary, component, model, and width — so one plan is built under several arms and the plan's own variance is out of the comparison (`target/eval/arms/s0-evals-rebuild-mode.patch`; the runner in the tree carries none of it). The runs log the Cursor backend at `debug`, so every shell command a build or verify turn ran is in the `run-1.build.stderr` as a `tool call` line, which is how the verify's checks are read.

The arms, in order: **S1**, the control, the write-path re-run above (`EVAL_RUNS=1 CURSOR_MODEL=composer-2.5 cargo run -p evals -- --build express-orders nestjs-pair`), which fills that section's results by its own rule and is the revision every rebuild arm builds; **S2**, the width arm, `EVAL_JOBS=1 --rebuild <S1> express-orders nestjs-pair`; **S3**, the layout arm, the same rebuild under a `node` whose `layout.md`, `build.md`, and `verify.md` make the root `package.json` static — `"workspaces": ["src/*"]`, the toolchain, the three scripts, and no package of the program's — and give each module its own `src/<stem>/package.json` naming the packages its files import, which `npm install` at the root installs into the root `node_modules`, so no manifest is ever written by two slices (`target/eval/arms/s3-per-stem-manifest.patch`, built from a detached worktree of this repository). The arm was first drafted as a manifest reserved to the bootstrap slice, the `start` stem's else `SLICE-001`, every other slice writing against Node's own modules or a local stand-in; it was redrawn before it ran, once S1's plan was read, because the sub-stem floor cuts the `start` stem into three slices (`bootstrap-infrastructure`, `application-runtime`, `http-middleware-and-errors`), two of them in wave 1 together, and a slice sees its own plan entry alone, so "the `start` stem's slice" named no one slice and the rule was not decidable where it mattered; the stand-in would also have had the `start` slice of a NestJS plan stand in for the framework. ### Predictions

- **H1, width delivers.** Slices built at once in a wave do not slow one another: on the case whose widest wave is three or more (`nestjs-pair`), the per-slice build turns at full width (S1) are within 1.25× of the same slices built one at a time (S2), median over the waves wider than one, and the wall-clock saving S1 realises over S2 is at least 70% of the `serial − critical` S2's turns predict. A ratio past 1.25 is contention — the pool (`CURSOR_MAX_AGENTS`, 8), `npm install` over one network, or the model's rate — and the per-slice ratio says which.
- **H2, the manifest conflict is systematic and a layout fixes it.** Under the shipped layout (S1, S2), every wave wider than one in which two slices each add a dependency conflicts at `package.json`, costing a build, a wave, and a verify; `src/index.ts` never conflicts. Under the per-stem manifest (S3), zero conflicts on both cases, the waves equal to the plan's, `covered` within five points of S1's, and no build turn slower than S1's by more than half; the cost to watch is a slice that adds to the root manifest against the rule, or a module whose own manifest lacks a package another module's files import, which `tsc` or the verify then reports.
- **H3, the verify is redundant on a one-slice wave.** The integrated tree after a one-slice wave is the slice's working copy the build turn already checked, so no verify fails on a one-slice wave across every run of this programme (at least ten such waves), while the verify is 35–55% of the serial time on every landed run.
- **H4, a conflict retry belongs inside the wave.** Deterministic: a conflicted slice rebuilt over the merged head before the wave's verify, rather than in the next wave, saves one verify per conflict; the figure is the verify durations of the waves a conflict added, read from S1 and S2.
- **H5, `covered` is self-reported and the verify checks compile and tests, not requirements.** The host's run of the layout's three checks disagrees with a passed verdict on at least one landed run (the instrumentation figure above says it will); 90% or more of scenarios have a test named by them exactly, the `then [unknown]` ones included, so the scenario-to-test figure is saturated and says nothing about what the test asserts; at least one file outside the layout per case; duplicate test names on at least one case; `then [unknown]` 15–25% of scenarios.
- **H6, a failed wave should be repaired, not re-run.** Where a `verify-failed` lands, the shipped repair resumes from the label and builds the failed wave's slices again from scratch, every turn of the wave paid once more; a repair turn over the integration copy would cost one turn. Read only where a verify fails.
- **H7, model-bound.** Under `gpt-5.3-codex` the same `express-orders` plan lands with build turns within 2× of `composer-2.5`'s either way, fewer tool calls a turn, and the host's checks agreeing with its verdict where `composer-2.5`'s did not. Descriptive, one run.
- **Observed, never decided on:** the tokens, the `write_files` calls a slice and the files each carries, the bytes a slice writes, and what the verify's shell commands were.

### Decision rule

- **H1 holds** when the median per-slice build-turn ratio S1 ÷ S2 over the waves wider than one is at most 1.25 and `wall(S2) − wall(S1)` is at least 0.7 × `(serial − critical)` of S2, on the case whose widest wave is three or more. Failing it, the per-slice ratio names the bound: a ratio under 1.25 with the wall saving short is the verify and the conflicts, not the width; a ratio past it is contention, and `--jobs` should default below the pool.
- **H2 holds** when S3 reports zero conflicts on both cases while S1 reports one or more on every case with a wave two or more wide, S3's waves equal the plan's, S3's `covered` is within five points of S1's, and no S3 build turn is slower than S1's by more than half. A coverage drop past five points, a slice writing the root manifest against the rule, or a verify failing on a package a module's manifest left out, is the rule costing what it saves, and the item becomes a `resolve` turn rather than the layout.
- **H3 holds** when no verify fails on a one-slice wave across every run, with at least ten such waves observed. It then asks the engine to make the verify of a one-slice wave the adapter's choice, or to skip it where the wave merged one slice over an unresumed head; a one-slice verify that fails refutes it whatever the count.
- **H4** is quantified, not decided: the verify time a conflict's extra wave cost, as the saving an in-wave retry would make.
- **H5** is read as the figures: a host check disagreeing with a passed verdict on any landed run is a `verify.md` defect first (what the verify ran is read from its `tool call` lines) and an engine item second (the host could run the adapter's checks itself); scenario-to-test coverage under 70% of the testable scenarios is a `build.md` item; a file outside the layout is a `verify.md` check-4 gap; a `then [unknown]` scenario with a test named by it is a test asserting nothing the specification states.
- **H6** is read only where a `verify-failed` lands; its figure is the resume's cost in turns against one repair turn, and a repair arm is built only if the figure is more than two turns.
- **H7** is descriptive: durations, tool calls, conflicts, and the fidelity figures side by side; no decision turns on one run of a second model.

**Decision, H2 — the manifest conflict is systematic and a layout fixes it, in part.** The first half holds on every shipped-layout run: `package.json` conflicted on every wave wider than one in which two slices added a dependency — S1 and S2 on both cases, S5a twice — and `src/index.ts` never did.
