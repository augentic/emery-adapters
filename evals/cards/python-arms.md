# The python adapter's arms

A round of the eval, run and read under [the protocol](README.md#protocol); [the README](README.md#rounds) indexes every round.

## The python adapter's first arms

The `python` adapter ships with the survey by model as its default from the first commit — the verdict of [the survey-default experiment](typescript-survey.md#the-survey-default-experiment) was earned on `typescript` and the Python adapter is built in its shape, with the model naming the surfaces and code deriving the rest — so its first cards are not a question of whether but of where the Python-specific rules earn their place. Three arms, each three runs under `composer-2.5` over the six authored cases ([evals/README.md](../README.md) describes them), each following [the protocol](README.md#protocol): predictions first, a decision rule, the card copied in while a decision rests on it. The two Python-specific rules under test have no feature flag; an "off" arm is a local edit to the one function named below, run and reverted, never shipped. The component suites pin what the survey decides by code over `click-jobs` and `fastapi-routers` with the survey's answer scripted (`python_fixture_click_jobs`, `python_fixture_fastapi_routers`), so a drift in those two cases' surfaces or stems on a card is the model's naming, not the derivation's.

### Arm 2 — the construction-at-load bootstrap

The rule under test: a module no script names and no guard runs is the bootstrap when, at load, it constructs something a package provides or calls a function of the tree that does — `wsgi.py`'s `app = create_app()` — which `Tree::bootstrap` reads through `runs_at_load` in `survey/surface.rs`. The off arm drops the construction clause from `runs_at_load`, leaving a guard, a script, or a conventional entry that calls something as the only ways a module runs. Over `flask-blueprints`, where the rule decides the bootstrap, and `fastapi-orders`, where the guard decides it and the rule must change nothing.

- **On (the baseline card).** `flask-blueprints` `4/4`, `start` present at `wsgi.py`: the factory's configuration and mounts, the timing hook, and the two error handlers — the three `start` requirements, after the first card dropped the one at the construction line itself (below) — under `start`, in stem.
- **Off.** `flask-blueprints` reads `3/4 -1` on 3/3 — no bootstrap, the brief says so, and `wsgi.py`'s `app` stands among the entry modules' exports — with the `start` requirements either missed or landing under `health` (the factory's module) as `0 in stem`; the risk worth seeing is the model naming `wsgi.py`'s `app` as a surface of its own, the signature of a rule the prompt would otherwise have to carry. `fastapi-orders` is unchanged, `2/2` on 3/3.

Decision rule: the rule stays when the off arm loses `start` on `flask-blueprints` on ≥ 2/3 runs and `fastapi-orders` is identical across the arms; it is narrowed — to a construction through a package alone, or to a function of the tree alone — if the on arm names a module the off arm does not and the expectation reads that module as no bootstrap on any of the six cases.

### Arm 3 — decorator anchors

The rule under test: a decorated `def` is listed in the facts, and accepted as a surface, at its whole span — `app/routers/orders.py#L40-L49`, the decorator through the last line of the body — so every line of a handler is a surface's own line and a requirement anywhere in it passes the anchor gate. The other arm lists and anchors the decorator through the `def` line alone (`#L40-L41`, `decorate` in `survey/parse/walk.rs` handed the head's lines), so a requirement inside a handler must land at a decision point, a `return`, a call through a package, or a step into the tree, as a requirement inside a registration's named handler must today.

- **Whole `def` (the baseline card).** Recall as the baseline; the restem and surface figures the same on both arms, since the stem and the id derive from the decorator and the route, which both arms read whole; the risk is a requirement anchored at a line that only wires inside a handler, which the prompt refuses in words and the gate cannot.
- **Decorator-plus-head.** One correction round more on some seams — a requirement re-anchored from a wiring line to the decision it states — and recall within one of the baseline on each case, with `fastapi-routers` and `django-shop` the cases where it may fall by two, since their handlers are the longest; `(entry, stem)` `Stability` identical; the anchors a requirement lands on more often at a decision point than at a handler's head.

Decision rule: the head arm replaces the whole-`def` rule when recall is within one requirement of the baseline on every case and at least one case's requirements move off handler heads onto the decisions they state (read from the misses-by-anchor and the matched anchors in the card); the whole `def` stays when the head arm costs a `budget exhausted` run or two requirements on any case.

## The python adapter's loop round

The four observations above set the round: the runner now writes the survey facts without a turn (`cargo run -p evals -- --facts <case>`, and every graded run's `run-N.facts.md`), grades a shared guard `in stem` under any of the stems its expectation lists, lays a small data file directly after the first module that names it, and the prompt reads a named value a requirement applies — a slice bound, a timeout handed to a call, a schema cap — as that requirement's criterion. Two real trees join the six authored cases, vendored as the `typescript` pair is and written from the facts dump and the code before any run: `fastapi-template` (FastAPI's own full-stack template, its `backend/`) and `django-styleguide` (HackSoft's styleguide example), [evals/README.md](../README.md) describes both. The dump showed four facts-level defects before a turn was spent, each fixed and pinned ahead of the baseline so the card measures the model's reading and not the derivation's: a `setup.py` beneath a package was dropped as the packaging script (`python_non_production`); Django's namespaced `include((module, namespace))` tuple mounted nothing, so every route under `api/` would have spelled its own segment as a stem — `create`, `start`, `finish` — in place of its application's (`python_mounts_namespaced`); and attrs' `define` and pydantic's `computed_field` were listed as decorator facts beside `dataclass` and `field_validator`, which were not (`python_decorated`). The arms that follow — the two cases' baseline, the decorator anchors (Arm 3), the construction-at-load bootstrap (Arm 2), and a second model — each follow the protocol: predictions first, the rule, the card copied in while a decision rests on it.
