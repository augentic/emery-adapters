# open-gap-fab — Proposal

## Why

Prove Vectis stays stub-faithful (or honestly closes build-editable GAP surfaces) when a My Lists FAB is wired with an unspecified activation outcome while an existing `NewList` page creates naming pressure — the open-GAP inventiveness desk-check.

## What Changes

- My Lists overview on a Crux shared core with a floating action button.
- `CreateList` Event is modelled and composition-wired; activation behaviour is intentionally unspecified pending operator criteria.
- `Page::NewList` already exists in the design (sibling / prior-slice screen) so B′ closure has a grounded destination if the build chooses to close.
- iOS shell only — project platforms are `core, ios`.

## Domains

### New Domains

- **my-lists** — list overview layout, FAB presence, and open-GAP FAB activation.

### Modified Domains

None — greenfield eval fixture (NewList is declared in design as an existing page variant, not authored by this slice's requirements).

## Platforms

- core
- ios

## Impact

- No persistence, no Android tree, no list CRUD beyond displaying static rows.
- Operator-curated `design-system/tokens.yaml` and `assets.yaml` supply theme and FAB icon.
