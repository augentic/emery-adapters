# Testing

Integration-first test posture for `emery-adapters`: integration owns every publicly reachable behavior, and the unit layer is deliberately thin. Design tests against the public surfaces — the WIT contract every component exports, which the component suites drive, and the public-contract live eval — never against private kernels. An adapter's one contract is the `source-adapter` world, so an adapter has no tests of its own: what it decides is asserted through the built component. Read this before adding, deleting, or relocating a test.

## The rungs

Every rung runs from this repository with its own `make` tasks; the engine repository tests itself independently. There is no cross-repo command surface.

Fastest feedback first. **Every behavior is asserted on exactly one rung** — duplicating an assertion across rungs is a defect, not extra safety.

| #   | Rung             | Owns                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Entry                                                          |
| --- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 1   | Component suites | Every `sources/*` component under the omnia runtime, driven by a guest program over `emery:adapter/source`: instantiation, effect-free `metadata`, the compiled-in prompt, and what the adapter itself decides — the seams its survey chose, seen as one completion each, and its fail-closed refusals; over fixture adapters, the SDK's side of the boundary, the WIT `error` arms, and the bindings' lowering of every record field; plus the embedded corpus of every adapter | `cargo nextest run -p emery-adapters` / `make test`            |
| 2   | Graded live eval | End-to-end spec generation over the adapter contract: prompt quality, the scorecard                                                                                                                                                                                                                                                                                                                                                                                              | operator-invoked, never CI (to be recreated as a root example) |

The live examples (`cargo build --workspace --target wasm32-wasip2 --release`, then `emery specify --config examples/<name>/emery.toml`) are not a rung: each walks one adapter through the shipped `emery` binary and the Cursor backend — extract, synthesis, the committed revision — asserting nothing. They are for watching a prompt change land in a specification, not for proving it — see [examples/README.md](../examples/README.md).

Ownership boundaries: omnia's `omnia-test` crate owns the reusable doubles and the fixture pipeline — the host-side `omnia_test::host::{ScriptedModel, Backends, Deployment, scratch}` the component suites drive, and `omnia_test::build::Components`, the nested `wasm32-wasip2` build behind `crates/test-programs`; the component suites own the component boundary and, over each shipped component, the adapter's own decisions, and link the omnia host stack through omnia-test (never an engine crate); the live eval owns grading and the scorecard, and stays a client of the shipped `emery` binary's public contract (architecture-review T6) — it never links engine crates, and CI never runs the live rung. The engine repository proves its own side of the boundary with its mock adapter; this repository proves every published component against the same runtime.

Sibling co-development: uncomment the path patches in the root `Cargo.toml` patch blocks to resolve engine crates from `../emery`. The committed tree uses git sources so CI can fetch the engine without a sibling checkout.

Testing a brand-new adapter: [authoring.md](authoring.md).

### 1. Component suites — `crates/test-programs`

The component rung follows omnia's `test-programs` pattern file for file. `crates/test-programs` is the fixture pipeline: its `build.rs` runs one `omnia_test::build::Components` build drawing from two sources — `scan_packages("sources").group("adapter")` compiles every `sources/*` adapter, the shipped `cdylib` components themselves rather than example stand-ins, as `ADAPTER_<NAME>` with a `foreach_adapter!` arm each; `scan("crates/test-programs/programs")` compiles every `programs/<group>/<scenario>.rs` as an `[[example]]` cdylib (the stanzas below the `# Generated by build.rs` marker in its `Cargo.toml` are regenerated by the build) into a `<GROUP>_<SCENARIO>` path constant and a `foreach_<group>!` completeness macro — a nested `wasm32-wasip2` build under `OUT_DIR`, incremental after the first build, written as one `gen.rs`. Natively the crate is that generated table and nothing else; on `wasm32` it is the programs' shared helpers (`src/helpers.rs`: the `Caller` side of the boundary, the checks a driver runs over what crosses it, and `maximal()`, the evidence with every record field populated). The crate has no tests of its own.

A program is one guest scenario: `#![cfg(target_arch = "wasm32")]`, `omnia_sdk::command!(scenario)`, an `async fn scenario()` that asserts what it observes and traps on failure. The group directory names the capability under test:

- `programs/source/` — the one driver over the `emery:adapter/source` interface, `extract`: `metadata` checked, then `extract` in the mode the host names as its arguments. None: over the lent workspace and over an inline value, each answer re-checked against the contract's claim gate on the caller's side. `refused <code>`: over the lent workspace, expected to fail and lift to that Omnia error class; `refused <code> <value>`: the same over `<value>` inline. `echoed`: over an inline value, expected to answer `maximal()` field for field. `together`: two `extract`s over the lent workspace dispatched at once, as the engine dispatches one per source, each answer re-checked.
- `programs/probe/` — fixture adapters (each exported with `emery_sdk::source_adapter!` over its own `metadata` and `extract` fns, as a shipped adapter is) that stand in for the adapter under test: `refusing` fails with `bad_request!` and `upstream` with `bad_gateway!`, one per WIT `error` arm; `echo` answers `maximal()` without a model call; `gated` mines an inline two-document corpus as one `Seam::Whole` — nothing of its own, so what it shows is the SDK's; `fanout` mines two `Seam::Note` seams whatever the input arm, so its `extract` holds two completions pending at once.

Host suites are the root package's, one flat file per subject over one shared runner. `tests/support/mod.rs` is the scenario support both component suites declare as `mod support;`: its `run(adapter, project, args, model)` describes the deployment through `omnia_test::host::Deployment` — the driver as the `wasi:cli/run` guest beside the component under test registered as `test_programs::ADAPTER` under the `emery:adapter/source` link, the project mounted read-only as `.`, the driver's mode as its arguments, the scripted host-side model (`omnia_test::host::ScriptedModel`, a `WasiModelCtx` double swapped into `Backends::defaults()`, or the support's `Barrier` around one, which answers a completion only once a party of them is pending and fails it after a bounded hold otherwise) — and requires `ExitStatus::SUCCESS` from the driver's own checks and the script exactly consumed, returning the model's record for the suite to assert on:

- Root `tests/source.rs` — `test_programs::foreach_adapter!()`, so every shipped component has a same-named test, and the adapter's further scenarios sit beside it as `<name>_<scenario>`. This is where what an adapter itself decides is asserted, through what the host sees of the component. Its survey shows as completions: a workspace `extract` opens one per seam, so the strict script — one gate-valid claims-only answer per seam, one more for the inline value — consumes exactly that many or the run fails, and each turn carries the seam's data, which the suite reads as data rather than phrasing: the paths a `Files` seam lists (`documentation_directories` asserts the paths of one top-level directory share a turn and appear in no other, and that a dot entry appears in none; `documentation_large_directory` asserts a directory of more than sixteen is cut by its subdirectories of two or more, its remainder one turn beside them or, when a lone document, in the first subdirectory's, and that a flat directory of twenty is not cut), the brief `intent` read through the mount (with the engine's own `spec.md`, `design.md`, and `.omnia/` staged beside it and not counted), the `- surface:` / `- entry:` lines `typescript` writes into each note (`typescript` scripts an inventory of three surfaces, two entering at one module, and asserts three extract turns name them, in any order, after one survey turn under the embedded `survey.md` and before the inline value's turn, which spends no survey). Its refusals run the driver's `refused` mode: `intent_not_one_file` and `intent_empty_brief` expect `bad_request` with no completion opened, the blank brief inline through `refused bad_request <value>`; `typescript_no_surface` expects it after the one survey turn, whose empty inventory the recorded `check` accepted, so the refusal is the adapter's and not a spent budget. What its `keep` refuses shows in the record too: `typescript_non_production` scripts an inventory entered at tests, a declaration file, a dependency, build output, a dot entry, and a file the adapter does not read, and asserts the first `check` exchange's correction names every entry while the second, over a production module, is accepted and alone reaches an extract turn. The `metadata` call opens no completion, and every extract turn's system is the compiled-in `extract.md`. Nothing here pins the SDK's brief text or a prompt phrase: a wording edit is not a behavior change.
- Root `tests/probe.rs` — `test_programs::foreach_probe!()`. `probe_refusing` and `probe_upstream` run the driver's `refused` mode, proving each WIT `error` arm lifts back to its Omnia class with no model turn consumed. `probe_echo` runs `echoed`, proving every field of the contract's records — each claim kind, both `backing` arms, every anchor form, extras that are objects, numbers, lists, and null — crosses the bindings as it left the adapter (extras ride as canonical JSON text and are parsed back), and that the kind the probe declares reaches the caller through `metadata` — the one place the source kind crosses the boundary. `probe_gated` runs the answered legs with `list_docs` and `read_doc` driven through the session, and asserts the SDK's side of the boundary once under the runtime: the embedded prompt as the system, the reference tools declared, `check` set, the adapter id and source key in the turn, the lend present for the workspace leg and absent for the inline one, the corpus answering both tools, and each candidate accepted by the guest's `check`; `gated_spent` runs `refused bad_request` over a candidate the gate rejects, proving the backend's spent budget crosses as `bad_request` with the correction naming the finding. `probe_fanout` runs the answered legs over a `Barrier` of two, proving the host property the SDK's fan-out rests on: the two completions one `extract` issues together are both pending before either is answered, so a host that serialised a guest's completions would fail inside the hold rather than hang. It is the permanent guard for that property, not a test of the SDK's join, which the SDK's own suite owns. `fanout_together` runs the same probe in the driver's `together` mode over a `Barrier` of four, proving the property the engine's fan-out over sources rests on: two link dispatches one caller issues together run together, so the two completions each opens are all pending before any is answered. A `Barrier` whose hold expires fails every completion after it, so a party the guest fills late — the SDK puts a seam whose turn failed upstream once more — cannot pass either guard; a failure inside the hold is a host finding to raise, never a reason to loosen the party. `probe_tracing`, `tracing_off`, and `tracing_default` run the `tracing` probe — four spans, INFO and DEBUG under its own target, DEBUG under `emery_sdk`, and DEBUG under a crate the guest merely depends on, with no filter of its own — through the support's traced runner, proving the level a caller names on the chain (the driver's `tracing <level>` mode, under `omnia_wasi_otel::LEVEL` as the engine's flags name it) decides what the adapter's tracing admits, over which crates: `debug` admits the INFO span, the probe's own DEBUG span, the `emery_sdk` DEBUG span, and the SDK's `source_adapter_extract` boundary span, but not the dependency's DEBUG; `off` admits nothing; and a caller that names no level dispatches an adapter that opens at omnia's `error`, admitting nothing — the engine always names one. `probe_telemetry` runs the `telemetry` probe — which narrows its own filter to `error` inside `extract` and opens an ERROR span — under `tracing info`, proving the boundary span omnia admitted at the caller's level survives the adapter's own reload beneath it.
- Root `tests/prose.rs` — `test_programs::foreach_adapter!()`, so every shipped adapter's corpus is checked (a new `sources/<name>` fails to compile here until a test of that name exists), over the adapter's own `PROSE` — each adapter crate is a native dev-dependency of the root for this, and the `rlib` beside its `cdylib` exists for it. Each test first holds the list to the tree, and to the prompts the SDK puts to the model by path (`extract.md`; `survey.md` too for an adapter that surveys by model), with `emery_sdk::check`, `emery_sdk::RUNTIME` as the imports: every `.md` under `prose/` is listed once; every relative link in a listed document — outside fenced code, its fragment dropped — names a listed document or one of those runtime references (`claims.md`, `reconciliation.md`), since `read_doc` answers from the table and then from `RUNTIME` and a directory, an unlisted file, or a path outside the tree is unreadable there; no listed document sits at a runtime reference's path, where it would answer for the SDK's; and every other listed document is reached from a prompt through those links, since what nothing links is embedded and never read. Then the two prompt rules nothing else enforces: `extract.md` stays under the 800 non-blank-line cap, and its `## Worked example` JSON fence parses as the SDK's `Evidence` (claims alone) and passes the claim gate — the one machine-checkable part of a prompt, so a prompt edit cannot teach the model a shape the adapter would refuse, and an engine pin that moves the contract (the required extras, the id grammar) fails here rather than in the live eval's repair rounds. Every document under `references/examples/` other than its `README.md` is a worked example too: the JSON fence under its `## Evidence` heading is parsed as `Evidence` and held to the same gate, with at least one claim, so `typescript`'s three examples cannot drift from the contract the prompt teaches. A `survey.md` is held to the same cap with a worked example that parses as the SDK's `survey::Inventory`; `typescript` requires it, since its survey is `server_error` without it, so its test reads it from the table and an unlisted one fails the suite. The prompts are read from the table, never from disk, so what is checked is what the component embeds. Nothing else about the corpus is asserted: the prompt each component embeds is proved under the runtime by `tests/source.rs`.

`foreach_source!` is generated but goes uninvoked: the one `source` program is the driver both component suites name directly, so there is no per-adapter test for a completeness macro to guard.

What every adapter shares is asserted once, never per adapter: the request shape — the declared tools, the schema format, the `check` flag, the workspace lend — the claim gate's in-place repair and spent-rounds refusal, the fan-out and the join, and the survey's check of each answered entry against the tree are the SDK's own suite's (`emery-sdk`'s `turn`, `extract`, `survey`, and `workspace` tests), and the gate once more under the runtime over the `gated` probe. The script is strict: a run past its end fails the completion the guest sees and the test, and a dropped script with unconsumed turns fails the test, so a scenario scripts exactly what its run consumes — a refusal before the model is reached scripts `ScriptedModel::default()`, and a survey candidate the check rejects consumes one scripted turn and records one `check` exchange before the next is offered. This rung never asserts prompt text or extraction quality — the SDK's suite owns what every adapter shares, the live eval owns quality.

```bash
cargo nextest run -p emery-adapters                 # the root suites: every component, the probes, the corpora
cargo nextest run -p emery-adapters --test source   # the shipped components alone
make test                                           # the whole workspace, matching CI
```

`nextest` is mandatory: each test runs in its own process, which is what lets environment-mutating suites pass. Never use bare `cargo test`.

The root is a package, so `make test` and the shared CI workflow pass `--workspace`, and so should any invocation meant to match them; every suite is the root package's today, so `cargo nextest run -p emery-adapters` runs the same tests.

The guest side — every program under `crates/test-programs/programs/` and the adapters' `survey` and `guest` modules — is `cfg(target_arch = "wasm32")`, which native clippy compiles to nothing, so `make lint` runs a second pass for `wasm32-wasip2`, where `clippy.toml`'s guest deny-list applies: `cargo clippy --workspace --exclude emery-adapters --lib --examples --target wasm32-wasip2 -- -D warnings` (the root package, native tests alone, is excluded). `make test` compiles that side only through the component build.

### 2. Graded live eval

Operator-invoked, never CI: the runner spawns the sibling shipped `emery` binary over the built components, drives one `specify` per case, records typed outcomes, grades the committed spec via `emery show spec`, and writes the dated scorecard. The runner is being recreated as a root example beside the live examples now that the fixture pipeline is in place; until then the live rung has no entry.

## Adding a test

Every behavior gets a home in exactly one place. Decide the home **before** writing the test:

| Home            | Location                                                                                | When                                                                                                                                                                                                                                                    |
| --------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Component**   | root `tests/source.rs`, `tests/probe.rs`, `tests/prose.rs`, over `crates/test-programs` | The subject is what an adapter decides (how its survey cuts a tree, a `Note` it writes, a fail-closed refusal — `source.rs`), the component boundary (instantiation, the bindings' lowering, the tool streams — `probe.rs`), or the corpus (`prose.rs`) |
| **Kernel unit** | `#[cfg(test)] mod tests` next to the code                                               | The branch is genuinely unreachable through the component's `extract` — with a one-line comment saying why; there are none today                                                                                                                        |

There is no crate-integration home: an adapter's `survey` is private guest code, compiled for `wasm32` alone, and its crate exports nothing but `PROSE`. Never add a test for what the SDK or the contract already proves (the request shape, the gate's repair loop, `Evidence` deserialization, the survey check against the tree), and never pin a prompt phrase or the SDK's brief text — prompt quality is the live eval's. Do not widen `pub` surface, or compile a module natively, solely for a test.

Shared support (`tests/support/mod.rs`) is compiled into every suite that declares it, and each suite uses a subset, so it carries `#![allow(dead_code, reason = "…")]` at its head — the module-level form the engine's lint posture already permits — rather than a `#[path]` module per suite. Test code is otherwise held to the same lints as the adapters.

Coverage is advisory here, not a gate: `make cov` (`cargo llvm-cov nextest --workspace`) instruments the native side alone, and every adapter runs inside wasmtime on the component rung, so its lines go uncounted.

## Test naming

Test function names are identifiers, not sentences — name the *scenario* (`gated_spent`, `documentation_directories`), never the outcome (`gated_spent_refused`, `documentation_directories_cut`). The enclosing `tests/<area>.rs` module already names the subject — don't restate it in every `fn`. A test a `foreach_<group>!` macro guards is the exception by construction: it carries its program's full `<group>_<scenario>` name (`probe_echo`) or its adapter's (`intent`), and since one file holds every adapter, an adapter's further scenarios lead with its name the same way (`intent_empty_brief`). Add a `//` comment only when the scenario and assertions do not expose its rationale.
